# 轻量对冲控制台稳定性任务编排文档

## 1. 执行目标

本任务编排用于把当前轻量版控制台从“可测试版本”推进到“可持续运行版本”。目标不是重写系统，也不是增加更多后台采集，而是在已经验证过的轻量核心基础上，完成 UI 排版、运行统计、账号剔除/恢复、三号降级阀门、局号停更标记、打包验收。

最终交付物：

- 最新真实 PyQt UI 采用 V5 排版，而不是只停留在静态 HTML 设计稿。
- 运行摘要、执行轮次、下注流水、单账号盈亏统计清晰准确。
- 余额不足或人工剔除后，剩余 3 个账号可继续运行，不再被已剔除账号阻塞。
- 被剔除账号可以在“本轮计划”区域主动安排下局恢复。
- 打包 exe 可由人工直接运行测试。
- 所有修改都有自测、人工验收点和回退边界。
- 不新增常驻资源监测、主界面调试日志、高频状态刷新或更积极的自动恢复。

## 2. 当前基线

当前已确认的运行基线：

- 最新打包入口：`LightweightHedgeConsole.spec`
- 实际启动入口：`bet_desktop/ui/run_lightweight_dashboard.py`
- 当前控制器：`bet_desktop/ui/lightweight_controller.py`
- 当前真实 UI：`bet_desktop/ui/lightweight_dashboard.py`
- 当前轻量核心适配：`bet_desktop/ui/lightweight_probe_adapter.py`
- 最新 exe 路径：
  - `dist/LightweightHedgeConsole/LightweightHedgeConsole.exe`
  - `release-candidates/LightweightHedgeConsole_20260626_three_account_gate_fix/LightweightHedgeConsole/LightweightHedgeConsole.exe`
- V5 静态排版稿：`docs/ui-drafts/lightweight-hedge-console-v5-layout.html`
- 稳定性方案文档：`docs/lightweight-runtime-stability-plan.md`

当前真实 exe 仍未采用 V5 排版。真实运行页目前仍是：

- 左侧：运行控制 + 高级设置
- 中间：账号状态 + 下注流水累计 + 执行轮次
- 右侧：本轮计划 + 运行摘要 + 单账号盈亏

V5 目标排版为：

- 左侧：运行控制 + 高级设置 + 下注流水累计
- 中间：账号状态 + 单账号盈亏
- 右侧：本轮计划 + 运行摘要
- 执行轮次表放入高级明细或折叠区
- 不再显示轻量日志区域

## 2.1 瘦身边界

本任务文档采用“目标保留、实现瘦身”的原则：

- 保留：同房、同局、可下注、余额、低余额剔除、限红、坐标、preflight、真实点击、实际金额、缺口、耗时。
- 保留：V5 排版、三号降级、人工剔除/恢复、盈亏统计、下注流水、最近执行明细。
- 降级：资源监测只做人工诊断报告，不进入常驻 UI。
- 降级：局号停更只默认做异常标记和发号隔离，不默认触发主动刷新、频繁重进房或重启浏览器。
- 降级：执行轮次表只展示最近 N 条，累计统计单独保存。
- 删除：主界面轻量日志/调试日志区域、测试发一轮/测试 10 轮主入口。

## 2.2 每任务执行前：最新 exe 相关源码复查门

每个任务开始前，执行 agent 必须先复查“最新已打包 exe 对应的真实源码路径”，确认该能力是否已经实现，避免重复开发或把已验证代码重写一遍。

必须复查：

- `LightweightHedgeConsole.spec`
- `bet_desktop/ui/run_lightweight_dashboard.py`
- `bet_desktop/ui/lightweight_dashboard.py`
- `bet_desktop/ui/lightweight_controller.py`
- `bet_desktop/ui/lightweight_probe_adapter.py`
- 与本任务直接相关的 `bet_desktop/ui/lightweight_models.py`、`bet_desktop/ui/lightweight_config_store.py`、`bet_desktop/tests/test_lightweight_hedge.py`
- 最新 exe 路径和修改时间：
  - `dist/LightweightHedgeConsole/LightweightHedgeConsole.exe`
  - `release-candidates/LightweightHedgeConsole_20260626_three_account_gate_fix/LightweightHedgeConsole/LightweightHedgeConsole.exe`

执行前必须输出一句复查结论：

- `已有能力，任务改为回归验证`
- `已有部分能力，只补缺口`
- `未实现，按任务最小实现`
- `涉及保护链路，暂停并请求确认`

禁止：

- 没有复查当前源码就直接按静态设计稿开发。
- 已经存在可用实现时重新写一套并替换。
- 为了统一风格重构接管、进房、状态采集、下注前检查或点击执行链路。

## 3. 最高约束

以下链路是当前项目最高保护区：

- 余额采集
- 局号采集
- 状态机判断
- 倒计时或可下注信号判断
- 房间号
- 限红
- 坐标定位
- 点击前检查
- 真实点击执行器

任何任务如果需要修改上述链路，必须先暂停实现，说明风险，并等待新的明确指令后才能动代码。

风险说明必须覆盖：

- UI 数据是否可能不同步
- 局号是否可能停更或误判
- 可下注状态是否可能误判
- 余额是否可能显示错误
- 房间号和限红是否可能绑定错误
- 坐标点击是否可能偏移
- 真实下注是否可能失败或重复点击

## 4. 总体实施顺序

必须按以下顺序推进，不能把高风险逻辑和低风险 UI 排版混在一起改。

1. 阶段 0：基线冻结，低风险，只读检查。
2. 阶段 1：V5 排版落地，低风险，只移动 UI 布局和样式。
3. 阶段 2：运行统计和显示修正，中风险，允许改统计数据结构，但不得改下注核心。
4. 阶段 3：计划卡片剔除/恢复 UI 状态，低到中风险，只记录人工意图，不影响发号。
5. 阶段 4：剔除/恢复接入计划和发号阀门，高风险，必须单独审核后执行。
6. 阶段 5：计划金额和筹码规则修正，高风险，必须单独审核后执行。
7. 阶段 6：局号停更诊断和安全隔离，高风险，必须单独审核后执行。
8. 阶段 7：登录、接管、进房体验验证，中风险，优先验证，谨慎修改。
9. 阶段 8：现有自动回房审计，中风险；如需新增恢复逻辑则升级为高风险并单独审核。
10. 阶段 9：真实下注前验收，高风险验证，不允许边测边改核心。
11. 阶段 10：打包 exe，中风险，只在源码验收通过后执行。
12. 阶段 11：手动资源诊断和多套运行容量，低风险，只人工触发采样和报告。
13. 阶段 12：最终审核，中风险，只审核和封版。

阶段 4、阶段 5、阶段 6、阶段 9 都可能影响发号、计划、房间、局号、可下注状态或真实点击，必须单独执行、单独验证、单独提交。阶段 8 默认只审计现有低频回房；如果要新增自动恢复动作，必须按高风险阶段处理。

用户已授权阶段 5-13 自动推进：不再逐阶段回问人类确认。人类只负责最终打包 exe 后的人工测试。阶段 5-13 执行前必须由独立 `gpt-5.5` 审核 agent 先发布该阶段独立完整任务编排文档；审核通过后，再交由另一个独立 `gpt-5.5` 执行 agent 实施、测试、中文提交。审核 agent 和执行 agent 不能是同一个 agent。

## 5. 高风险阶段额外门禁

阶段 5-13 不再等待人类逐阶段确认。阶段 5、阶段 6、阶段 9，以及任何需要新增自动恢复动作的阶段 8 修改前，必须先暂停代码实施，由独立 `gpt-5.5` 审核 agent 发布该阶段独立完整任务编排文档，并明确审核结论为 `通过` 后，才能交给另一个独立 `gpt-5.5` 执行 agent 修改代码。

风险说明必须逐项覆盖：

- 余额是否可能误判，尤其是余额未知、过期、读取失败。
- 局号是否可能停更、误读、截断不一致。
- 状态机和可下注窗口是否可能误判。
- 倒计时或前端本地倒计时是否可能与真实下注窗口偏离。
- 房间号、目标房间、已进房房间是否可能不一致。
- 限红和单号金额范围是否可能被突破。
- 坐标、筹码点击区域、下注区域是否可能偏移。
- 点击前检查是否可能被绕过。
- 真实点击执行器是否可能收到错误账号或已剔除账号。

高风险阶段执行要求：

- 每个高风险阶段必须单独提交，不能和 UI 排版、样式、日志整理混改。
- 每个高风险阶段必须先补测试或明确已有测试，再改实现。
- 每个高风险阶段必须保留回退点。
- 任何真实下注相关变更必须先通过源码测试，再进入人工观察。
- 每个高风险阶段也必须先完成第 2.2 节源码复查门；若发现最新 exe 相关代码已具备能力，只允许补测试或 UI 接口，不允许重复实现核心链路。
- 阶段 5-13 的每个阶段都必须产出或更新一份独立执行记录，包含：审核 agent 结论、执行 agent 结论、变更文件、测试命令、测试结果、commit hash。
- 阶段 5-13 执行 agent 完成一个阶段并自测通过后，必须自动继续下一阶段的审核流程，直到阶段 13 完成并打包 exe。

## 6. 任务状态规则

每个任务使用以下状态：

- `[ ]` 未开始
- `[~]` 执行中
- `[x]` 已完成
- `[!]` 阻塞

每个阶段完成后必须记录：

- 改了哪些文件

## 7. 余额未知和数据过期规则

计划生成、恢复账号、低余额剔除都必须明确处理余额数据状态。

默认规则：

- 余额低于低余额剔除线：不得参与新计划。
- 余额读取失败、未知、过期：不得作为恢复账号重新参与计划。
- 余额未知的正常账号是否继续参与，必须由阶段 4 在实现前明确规则并补测试，不能默认为安全。
- 已剔除账号余额未知，不得阻塞剩余 3 个账号发号。
- 若余额数据过期但账号已经在本轮计划内，不得在点击中途临时改变本轮计划。

说明：当前代码中 `_balance_covers()` 对余额未知存在放行行为，阶段 4 必须先审计并明确是否保留、收紧或只在测试模式放行。

### 盈亏公式

推荐使用：

`当前盈亏 = 当前余额 - 初始余额 - 累计充值 + 累计提现`

说明：

- 充值不应该被误算成盈利。
- 提现不应该被误算成亏损。
- 初始余额只在本次 UI 进程启动后首次读取余额时设定。

- 手动录入充值/提现后，每个账号盈亏独立正确变化。
- UI 长时间运行不会因为表格无限增长而明显变卡。

## 21. Agent 分工

### gpt-5.5 审核 Agent

职责：

- 审核需求、设计、任务是否完整。
- 审核是否误触最高保护链路。
- 审核每个阶段验收是否明确。
- 审核风险分级是否合理。
- 对阶段 5-13 的每个阶段，先发布独立完整任务编排文档，文档必须包含：目标、允许修改范围、禁止修改范围、源码复查清单、测试门、回退点、完成记录格式。

不得：

- 直接改真实下注核心。
- 跳过阶段顺序。
- 与执行 agent 合并为同一个 agent。

输出：

- `通过`
- 或列出必须修正的问题。

### gpt-5.5 执行 Agent

职责：

- 只按审核 agent 已通过的独立任务编排文档执行。
- 每次只执行一个阶段。
- 每个任务执行前先完成第 2.2 节“最新 exe 相关源码复查门”，并在输出中写明已有能力、缺口和本次最小改动范围。
- 修改前确认该阶段允许修改的文件范围。
- 修改后运行对应测试。
- 自审通过后更新任务完成记录，创建中文 commit。
- 输出变更文件、测试结果、commit hash、是否进入下一阶段。

不得：

- 擅自重构轻量核心。
- 擅自恢复旧 UI worker。
- 擅自增加高频 canvas 探针。
- 擅自增加常驻资源监测、主界面调试日志或主动高频恢复。
- 擅自修改坐标、局号、余额、状态机链路。

阶段 5-13 自动推进规则：

1. 审核 agent 发布并通过阶段 N 独立任务编排文档。
2. 执行 agent 只按阶段 N 文档执行。
3. 执行 agent 自测通过并创建中文 commit。
4. 主 agent 复核提交、工作区和测试摘要。
5. 若阶段 N 完成，则自动进入阶段 N+1 审核流程。
6. 阶段 13 完成后打包 exe，并把 exe 路径交给人类测试。
