# 轻量对冲控制台稳定性设计

## 总体设计

轻量 UI 只订阅轻量核心已经产出的状态、计划和执行结果。UI 不主动高频扫描游戏画面，不直接参与坐标定位，不绕过轻量核心的下注前检查。

数据流：

1. 浏览器适配层维护 a1/a2/a3/a4 页面和会话。
2. 轻量核心读取必要状态：房间、局号、余额、可下注信号、坐标缓存。
3. 计划生成器基于当前主号、余额、低余额线、筹码组合生成本轮计划。
4. 执行器并行下发真实点击，并返回实际金额、缺口、耗时、失败原因。
5. UI 只展示状态、计划、最近执行明细、流水、盈亏和最小事件摘要。

## UI 设计

### 账号状态卡片

显示：
- 平台名或 aX。
- 主/副身份。
- 可下注/不可下注。
- 房间号。
- 局号，展示时去掉无意义尾部差异字段，仅保留用于人工识别的一致部分。
- 当前余额。
- 目标房间。
- 进房进度。
- 单账号按钮：重启、接管、进房。

颜色：
- 可下注：绿色。
- 不可下注：蓝色。
- 异常/需人工：红色或警示色。

### 本轮计划

显示：
- 计划轮次。
- 主号土黄色金额块。
- 副号普通金额块。
- 每个账号的中文方向：庄/闲。
- 筹码组合和点击间隔。

### 运行摘要

显示：
- 测试/执行轮次。
- 总缺口。
- 最慢整轮。
- 最慢点击。
- 运行时间。
- 当前状态：正常、等待、暂停、停止、需人工。
- 最近一次停止/等待原因。

### 单账号盈亏

显示：
- aX + 平台名。
- 初始余额。
- 当前余额。
- 累计充值。
- 累计提现。
- 当前盈亏。

统计公式：

`当前盈亏 = 当前余额 - 初始余额 - 累计充值 + 累计提现`

初始余额只在 UI 本次启动后第一次读到该账号余额时设置。暂停、停止、重新启动轻量控制不重置初始余额。

### 下注流水累计

原发号门槛区域替换为四个账号的实际下注流水累计：
- a1/a2/a3/a4 或平台名。
- 累计实际下注金额。
- 重置流水按钮。

累计来源只使用执行结果中的实际下注金额。

## 核心逻辑设计

### 余额不足剔除

计划生成前过滤账号：
- 余额低于低余额剔除线：剔除。
- 余额不足以覆盖本轮计划：剔除并重排。

主号继承：
- 若原主号不可用，在剩余账号中选择当前余额最多者作为新主号。
- 剩余账号不足 3 个时停止发号。

### 筹码拆分

筹码面额必须来自平台实际支持面额，包括 4 元筹码。拆分目标：
- 每账号不超过 5 步。
- 优先减少缺口。
- 避免生成没有对应筹码的金额。
- 副号金额允许合理扰动，但不得突破步数和余额限制。
- 副号扰动验收按最近 20 个完整计划检查：同一副号至少出现 2 种合法金额组合，除非配置或余额限制只允许一种组合。

### 倒计时展示

UI 倒计时是展示层倒计时：
- 后端捕捉到新局可下注信号时发送一次事件。
- UI 从 12 秒开始本地倒计时。
- 到 0 后转不可下注。

真实下注仍由轻量核心在点击前做同房、同局、可下注和页面状态检查。

### 进房并行

批量进房发起后，四个账号并行执行：
- 每个账号独立记录目标房间、阶段、耗时和错误。
- 单个账号失败不阻塞其他账号。
- 已在目标房间的账号直接标记完成。

## 78 轮后中断诊断

轻量核心需要在停止或无法继续时给 UI 一个明确原因：
- `manual_pause`
- `manual_stop`
- `insufficient_accounts`
- `low_balance`
- `room_not_ready`
- `wait_betting_timeout`
- `browser_disconnected`
- `execution_exception`

可恢复原因继续等待，或沿用现有低频自动回房机制；不可恢复原因停止发号并提示人工处理。不得为了诊断新增更频繁的后台扫描。

等待下注窗口超时时必须记录一次诊断快照：
- 当前轮次。
- 等待耗时。
- 参与账号的房间、局号、余额、可下注状态摘要。
- 进房阶段摘要。
- 是否处于等待下一局或现有自动回房流程。

## 局号停更设计

局号停更处理分两层：

1. 默认层：只标记“局号停更/数据过期”，并禁止该账号作为正常账号参与发号。
2. 恢复层：仅在单独确认后评估是否沿用现有低频回房机制，不默认新增主动刷新、重进房或重启浏览器。

局号停更不应和“不可下注”混淆。不可下注是正常游戏阶段；局号停更是状态数据异常。

## 手动资源诊断设计

采用人工触发的一次性采样：
- Python/UI 进程内存。
- Chromium/Chrome 进程内存。
- CPU 采样。
- 浏览器实例数量。

不新增常驻资源监测线程，不在主界面持续显示资源曲线。容量估算按当前一套轻量 UI 的浏览器数、内存和 CPU 峰值做保守估计。

估算公式：
- `内存套数 = floor((可用内存 * 0.7) / 单套增量内存)`
- `CPU套数 = floor(70 / 单套平均CPU百分比)`
- `浏览器套数 = floor(建议最大浏览器进程数 / 单套浏览器进程数)`
- `最终建议套数 = min(内存套数, CPU套数, 浏览器套数)`

若无法测得单套增量，先用当前一套轻量 UI 的 Python 进程、WebView 进程、相关 Chrome 进程总内存作为保守上限。

## Interfaces

- UI 接口：只消费控制器已经缓存的账号状态、当前计划、最近执行结果、累计统计和最小事件摘要。
- 控制器接口：只从 adapter 事件队列接收状态，不允许 UI 为展示主动扫描游戏页面。
- 资源诊断接口：仅人工触发，输出报告，不作为运行循环的一部分。

## Data Model

- `account_status`：账号当前展示状态，来源于轻量核心事件。
- `current_plan`：本轮计划，只保留当前轮用于展示。
- `recent_round_results`：最近 N 条执行明细，用于查看最近缺口和耗时。
- `cumulative_stats`：累计轮次、总缺口、流水、最慢耗时，不随最近表格裁剪。
- `profit_state`：初始余额、当前余额、累计充值、累计提现、当前盈亏。

## Error Handling

- 状态缺失或局号停更时，先标记异常并阻止其作为正常账号参与发号。
- 已剔除或异常账号不得阻塞剩余可用账号的同房同局判断。
- 自动回房只沿用现有低频冷却机制；不得在真实点击期间触发恢复动作。
- 不可恢复错误必须显示固定原因码并停止真实发号。

## Configuration

- 可配置项保留：房间、主号、金额范围、点击间隔、确认等待、低余额剔除线、最近明细保留条数。
- 不新增资源监测刷新间隔、日志刷新间隔、canvas 探针频率等容易变重的配置项。

## Test Strategy

- UI 排版和统计测试不得依赖真实浏览器采集。
- 计划、剔除、筹码、发号阀门测试必须覆盖 4 号和 3 号两种模式。
- 局号停更测试默认只验证“标记异常、不参与发号、不高频刷新”。
- 资源诊断测试只验证人工触发报告格式，不验证常驻刷新。

## 风险控制

不得修改：
- 坐标识别算法。
- 点击前检查逻辑。
- 真正下注点击函数。
- 状态采集主路径。

需要修改上述区域时，必须重新向用户说明风险并获得明确继续指令。

## 测试策略

自动测试：
- 筹码拆分含 4 元。
- 低余额剔除和主号继承。
- 盈亏公式含充值/提现。
- UI 配置保存和读取。
- 执行结果更新流水累计。

人工测试：
- a1/a2/a3/a4 分别打开登录页并填写。
- 批量并行进房 1/2/3 房。
- a2 有头、其他无头时启动持续对冲。
- 模拟一个账号余额不足。
- 模拟充值/提现统计修正。
