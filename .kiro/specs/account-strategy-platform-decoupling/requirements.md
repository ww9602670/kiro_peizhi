# 账号与策略平台类型彻底解耦

## 目标

把当前“账号预先绑定 JND28WEB/JND282，再要求策略平台必须等于账号平台”的旧模型彻底移除，改成下面这套新模型：

1. 账号只绑定“游戏类型”与站点地址，不再预先绑定“网盘/2.0”。
2. 策略在创建时独立选择运行平台类型。
3. 运行时按 `(account_id, platform_type)` 隔离，不允许一个账号 worker 用单一平台上下文去执行另一种平台策略。
4. 旧链路在确认无业务价值后直接清理，不保留长期双轨屎山。

## 术语

- `game_type`
  - `JND28`
  - `LUCKYSB`
- `platform_type`
  - `JND28WEB`
  - `JND282`
  - `LUCKYSB`

规则：

- 一个 `JND28` 账号允许创建 `JND28WEB` 和 `JND282` 策略。
- 一个 `LUCKYSB` 账号只允许创建 `LUCKYSB` 策略。

## 必须满足的结果

### R1. 账号绑定模型改为 game_type

1. 绑定账号时，前后端都只选择 `game_type`，不再要求用户先绑定 `JND28WEB/JND282`。
2. 加拿大账号必须继续要求填写站点地址。
3. 绑定账号时做的只是“账号有效性校验”，不能把账号永久锁定为某个运行平台类型。

### R2. 策略独立选择 platform_type

1. 创建策略时，由策略自身决定 `platform_type`。
2. 后端不再要求 `strategy.platform_type == account.platform_type`。
3. 后端改为校验 `strategy.platform_type` 是否属于 `account.game_type` 允许的集合。

### R3. 运行时按 `(account_id, platform_type)` 隔离

1. 同一个账号下的 `JND28WEB` 策略与 `JND282` 策略必须分别进入独立运行时上下文。
2. 每个运行时上下文都必须拥有自己的：
   - 期号轮询状态
   - 当前期执行计划
   - 赔率缓存
   - 会话状态
   - 告警上下文
3. 不允许再出现“同一个账号 worker 只拿第一个运行中策略的平台类型，然后拿它去跑全部策略”的实现。

### R4. 会话与风控必须按平台上下文工作

1. 风控检查不能再只看 `gambling_accounts.session_token`。
2. 会话状态必须能区分 `(account_id, platform_type)`。
3. 同一个账号下，不同平台运行时的登录、心跳、重连、失效告警必须互不串线。

### R5. 赔率缓存必须按平台隔离

1. 当前 `account_odds` 只按 `account_id` 存储的模型必须升级。
2. 网盘与 2.0 的赔率不能再共用同一份缓存。
3. 人工确认赔率的动作必须明确作用于某个 `platform_type`。

### R6. 订单必须记录实际执行平台

1. `bet_orders` 必须记录下单时的实际平台类型快照。
2. 结算、对账、补偿、追查都必须优先使用订单快照，不得依赖当前账号配置或当前策略配置反推。

### R7. 旧 JND 重复账号必须迁移并合并

1. 当前因为旧模型造成的“同站点、同账号、同操作者，但拆成 JND28WEB/JND282 两个账号”的历史数据必须识别出来。
2. 必须提供合并迁移方案，把重复 JND 账号收敛成单个 `JND28` 账号。
3. 迁移后，原有策略、订单、对账数据不能丢。

### R8. 前端模型必须同步彻底调整

1. 账号页不再显示 JND 的 `JND28WEB/JND282` 账号绑定选项。
2. 创建策略页改为根据账号的 `game_type` 展示允许的 `platform_type`。
3. 前端不得再提交 `WEB` / `2.0` 这类纯展示值给后端。

### R9. 旧链路必须按门槛删除

以下旧链路必须进入删除清单：

1. 账号层 `platform_type` 绑定逻辑。
2. `strategy.platform_type must match account.platform_type` 校验。
3. manager 以账号为单位只启动一个固定平台 worker 的逻辑。
4. `account_odds` 的单账号单缓存模型。
5. `gambling_accounts.session_token` 作为唯一会话依据的逻辑。
6. 前端 `WEB` / `2.0` 伪平台值。

删除前必须满足：

1. 新表/新字段已完成迁移。
2. 双读双写回退命中为 0。
3. 回归测试与人工验收通过。

## 验收标准

### A1. 创建与保存

1. 同一个 `JND28` 账号下可创建 `JND28WEB` 策略。
2. 同一个 `JND28` 账号下可创建 `JND282` 策略。
3. 同一个 `JND28` 账号下同时存在两类策略时，不再出现 `platform_type must match account platform_type`。

### A2. 执行与结算

1. 同账号下网盘策略只走网盘运行时。
2. 同账号下 2.0 策略只走 2.0 运行时。
3. 同期执行时，两类策略不会互相污染期号、赔率、下单、结算、对账结果。

### A3. 赔率与会话

1. 刷新网盘赔率不会覆盖 2.0 赔率。
2. 刷新 2.0 赔率不会覆盖网盘赔率。
3. 一个平台会话失效时，不会把另一平台运行时误判为掉线。

### A4. 迁移与清理

1. 旧 JND 双账号样本迁移后，策略和订单仍能查到。
2. 旧兼容回退代码在最终清理后，相关测试仍全绿。
3. 仓库内不再存在新的调用链继续依赖账号层 `platform_type == 策略层 platform_type` 这个旧假设。
