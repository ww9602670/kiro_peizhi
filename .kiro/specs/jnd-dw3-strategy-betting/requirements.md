# JND 三字定位策略下注需求文档

## 1. 文档目标

本文档定义 JND 三字定位（DW3）在“策略下注”场景下的正式需求边界，用于约束后续实现、测试、验收。

本轮需求已经不是“选组后每期都下”的旧模型，而是以下新模型：

- 操作者在策略页选择 `WEB` 或 `2.0`
- 操作者在两个 tab 中多选 16 个 DW3 组合
- 操作者再选择“最近 N 期组信号阀门”
- 系统在每次下注前先根据最近 N 期已开奖数据过滤掉已出现过的组
- 剩余组再映射为具体 `DW3_xxx`
- 同号不是简单去重，而是金额叠加
- 合并后的唯一号码列表以单请求方式向平台发起下注

本次范围只覆盖：

- DW3 策略下注
- `WEB` 与 `2.0`
- 16 组组合选择
- 最近 N 期组信号阀门
- 合并号码、金额叠加、单请求提交
- 平台真实结果结算

本次范围明确不包含：

- 新增 DW3 手工下注页
- 任意输入 `123,124,125` 的自由选号模式
- 新的 martingale 触发规则
- `DW4` 或其他定位玩法

## 2. 术语和冻结定义

### 2.1 平台定义

- `WEB` 指 `lotteryType=JND28WEB`
- `2.0` 指 `lotteryType=JND282`

### 2.2 DW3 具体号码

- DW3 具体下注字段定义为 `DW3_000` 到 `DW3_999`
- 三位号码必须保留前导零，例如 `001`、`038`

### 2.3 组合族定义

- `大小组合` 使用三位上的“大/小”覆盖 DW3
- `单双组合` 使用三位上的“单/双”覆盖 DW3

### 2.4 单位定义

- 大：`5,6,7,8,9`
- 小：`0,1,2,3,4`
- 单：`1,3,5,7,9`
- 双：`0,2,4,6,8`

### 2.5 16 个正式组合编码

系统内部必须使用稳定的组合编码，不允许只存中文标签。

#### 大小组合编码

| 中文标签 | 内部编码 |
| --- | --- |
| 大大大 | `DW3_BS_BBB` |
| 大大小 | `DW3_BS_BBS` |
| 大小大 | `DW3_BS_BSB` |
| 大小小 | `DW3_BS_BSS` |
| 小大大 | `DW3_BS_SBB` |
| 小大小 | `DW3_BS_SBS` |
| 小小大 | `DW3_BS_SSB` |
| 小小小 | `DW3_BS_SSS` |

#### 单双组合编码

| 中文标签 | 内部编码 |
| --- | --- |
| 单单单 | `DW3_OE_OOO` |
| 单单双 | `DW3_OE_OOE` |
| 单双单 | `DW3_OE_OEO` |
| 单双双 | `DW3_OE_OEE` |
| 双单单 | `DW3_OE_EOO` |
| 双单双 | `DW3_OE_EOE` |
| 双双单 | `DW3_OE_EEO` |
| 双双双 | `DW3_OE_EEE` |

其中：

- `B` 表示大
- `S` 表示小
- `O` 表示单
- `E` 表示双

### 2.6 组信号定义

每期开奖结果只会产生两个 DW3 组信号：

- 1 个大小组信号
- 1 个单双组信号

例如开奖 `321`，其组信号固定为：

- 大小组：`DW3_BS_SSS`（小小小）
- 单双组：`DW3_OE_OEO`（单双单）

### 2.7 最近 N 期组信号阀门

“最近 N 期没有开过的组才下注”冻结为以下规则：

1. `N` 表示最近 `N` 期已开奖期数，且由操作者选择。
2. 过滤对象是“组”，不是具体号码。
3. 最近 `N` 期里只要某个组出现过至少一次，该组就被视为本期屏蔽组。
4. 大小组和单双组分别过滤，不能混算。
5. `N=3` 与 `N=1` 是同一套规则，只是窗口更大。

形式化定义如下：

- `selected_bs`：操作者选中的大小组集合
- `selected_oe`：操作者选中的单双组集合
- `blocked_bs`：最近 `N` 期出现过的大小组集合
- `blocked_oe`：最近 `N` 期出现过的单双组集合
- `effective_bs = selected_bs - blocked_bs`
- `effective_oe = selected_oe - blocked_oe`

### 2.8 金额叠加定义

每个具体号码只属于：

- 1 个大小组
- 1 个单双组

因此同一个具体号码的最终下注金额必须按“组命中份数”叠加，而不是简单并集去重。

定义如下：

- `stage_amount`：当前马丁阶段对应的单号码基础金额
- `bs_token(x)`：号码 `x` 的大小组
- `oe_token(x)`：号码 `x` 的单双组
- `multiplier(x) = 1{bs_token(x) in effective_bs} + 1{oe_token(x) in effective_oe}`
- `amount(x) = stage_amount * multiplier(x)`

因此：

- `multiplier=0`：该号码本期不下注
- `multiplier=1`：该号码下注 1 份当前阶段金额
- `multiplier=2`：该号码下注 2 份当前阶段金额

当前 DW3 只有两组族，因此 `multiplier` 的合法值只能是 `0/1/2`。

### 2.9 跳过期定义

如果本期阀门过滤后：

- `effective_bs` 和 `effective_oe` 都为空，或
- 合并后的所有具体号码金额都为 `0`

则本期必须记为“阀门跳过”，不向平台发起下注。

阀门跳过时：

- 不算赢
- 不算输
- martingale 阶段不推进
- martingale 阶段也不重置

### 2.10 单请求提交目标

本轮最终实现目标冻结为：

- 合并号码
- 去掉金额为 `0` 的号码
- 对重复号码做金额叠加
- 将全部有效号码以单次 `Confirmbet` 请求提交

系统不得把“默认分批提交”当成正式目标。

如果实站真实下注验收门证明某个平台不接受该类单请求大包：

- 必须停止宣布该能力已支持
- 必须回到规格修订
- 不得静默降级成默认分批并继续声称符合本需求

## 3. 已冻结证据

以下证据是本次需求的事实基础，后续实现不得脱离这些证据自行想象：

- `backend/probes/three_digit/20260418_013658/`
  - `JND28WEB` 的 DW3 页面、赔率加载证据
- `backend/probes/live_dw3_bet/20260418_014833/`
  - `JND28WEB` 的真实下注、返回、结算证据
- `backend/probes/three_digit/20260418_023315/`
  - `JND282` 的 DW3 页面、赔率加载、共享脚本证据
- `backend/probes/live_dw3_bet_2p0/20260418_025714/`
  - `JND282` 的真实下注、返回、结算证据

从证据冻结出以下结论：

- `WEB` 和 `2.0` 的 DW3 赔率都必须通过 `settingCode=DW3` 获取
- `midCode=DW3` 不能用于 DW3 赔率加载
- `JND282` 页面明确存在 `DW3` 页面和 `lotteryType=JND282`
- `WEB` 与 `2.0` 的 DW3 下单都已验证接受 `betdata[] + lotteryType + betNum + prompt + gt + install`
- `Result` 必须以平台返回为准，不允许自行重算
- DW3 结算匹配不能依赖 `MidCode`
- 共享脚本内存在 `MAX_BET=126`

同时必须明确：

- `MAX_BET=126` 目前只是页面脚本证据
- 它不能直接当成服务器真实上限
- “单请求可提交数百到上千号码”尚未被我们自己实站验证
- 因此单请求大包能力必须经过新的实站真实下注验收门

## 4. 功能需求

### 4.1 策略页 UI 形态

1. DW3 只能出现在“策略下注”入口，不新增独立手工下注页。
2. 前端必须允许操作者在 DW3 策略中选择平台：
   - `WEB`
   - `2.0`
3. 前端必须允许操作者选择最近 `N` 期组信号阀门。
4. 前端必须展示两个 tab：
   - `大小组合`
   - `单双组合`
5. `大小组合` tab 必须展示 8 个可多选项。
6. `单双组合` tab 必须展示 8 个可多选项。
7. 前端不得渲染 `DW3_000` 到 `DW3_999` 的 1000 项勾选器。
8. 前端必须支持跨 tab 多选。
9. 前端必须清楚提示：
   - 金额窗口表示“每个具体号码的基础金额”
   - 实际本期下注金额会受最近 `N` 期阀门影响
10. 前端至少要展示：
   - 已选大小组数量
   - 已选单双组数量
   - 当前阶段基础金额
   - 理论最大总下注额说明

### 4.2 保存和传输格式

1. DW3 策略保存时必须存储稳定组合编码，不允许只存中文标签。
2. DW3 策略保存时不得把 1000 个具体号码直接存入 `strategies.play_code`。
3. `N` 必须作为独立策略参数保存，不得编码进 `play_code`。
4. 系统必须支持对 DW3 策略再次编辑并保留原平台、原组选择、原阀门期数。
5. 现有 `flat / martin` 策略必须允许更新 DW3 的 `play_code` 与阀门参数。

### 4.3 组阀门规则

1. 每期下注前，系统必须基于“最近 `N` 期已开奖数据”生成 `blocked_bs` 与 `blocked_oe`。
2. 大小组只与大小组比较，单双组只与单双组比较。
3. 只要某组在最近 `N` 期出现过至少一次，该组本期就不得参与下注。
4. 系统不得把“最近 N 期没开过的号码才下注”误实现成“按具体号码过滤”。
5. 阀门使用的数据必须来自最近 `N` 期已完成开奖，不得把当前待下注期混入窗口。
6. 如果最近开奖数据不足以形成可靠阀门判定，本期 DW3 必须跳过并记录原因。

### 4.4 金额、叠加与总额规则

1. DW3 必须继续复用当前策略页的金额窗口，不新增独立金额控件。
2. 当前金额窗口在 DW3 模式下的含义必须固定为“每个具体号码的基础金额”。
3. 马丁序列在 DW3 模式下的每个阶段值，也必须解释为“每个具体号码的基础金额”。
4. 系统必须按“同号金额叠加”生成最终下注金额，不得只做并集去重。
5. 系统必须支持同一个号码在同一期被叠加成 `2` 倍基础金额。
6. 本期总下注额必须按所有最终号码金额求和。
7. 基于 DW3 两个组族的数学特征，本期总下注额必须等价于：
   - `125 × stage_amount × (effective_bs_count + effective_oe_count)`
8. 以前端示例说明：若操作者选中全部 16 组，阀门 `N=1`，最近 1 期开奖为 `321`，则本期必须屏蔽：
   - `DW3_BS_SSS`
   - `DW3_OE_OEO`
9. 上例中其余组继续参与下注，重复号码金额需要叠加后再提交。
10. 若只选 `大大大`，基础金额为 `1`，马丁序列为 `1,3,5`，则：
    - 第一期总下注额为 `125 × 1 = 125`
    - 若未中，第二期总下注额为 `125 × 3 = 375`
    - 若再未中，第三期总下注额为 `125 × 5 = 625`
11. 若本期因阀门跳过没有发生真实下注，则 martingale 阶段保持不变。
12. 若本期真实下注且命中开奖号码三位精确组合，则 martingale 重置到第一阶段。
13. 若本期真实下注且未命中，则 martingale 推进到下一阶段。

### 4.5 赔率加载

1. `WEB` 的 DW3 赔率加载必须使用 `settingCode=DW3`。
2. `2.0` 的 DW3 赔率加载必须使用 `settingCode=DW3`。
3. 系统不得继续用 `midCode=DW3` 作为 DW3 赔率来源。
4. 如果某期开奖未成功拿到 1000 个 DW3 赔率，系统必须中止该期 DW3 执行并记录原因。
5. 系统必须为最终提交的每个具体号码绑定它自己的赔率值，不得假定所有号码恒定同赔。

### 4.6 下单规则

1. DW3 下单必须使用平台原生 `betdata[]` 结构。
2. DW3 下单请求必须带上：
   - `lotteryType`
   - `betNum`
   - `prompt`
   - `gt`
   - `install`
3. 本轮正式目标是“单请求提交合并后的唯一号码列表”，不得默认走分批。
4. 发送给平台的每条 `betdata[i]` 必须对应一个唯一具体号码及其最终叠加后的金额。
5. 金额为 `0` 的号码不得出现在请求体中。
6. 如果单请求被平台拒绝，系统必须将其标记为兼容性阻断问题并保留证据，不得静默拆批重试后继续声称需求完成。
7. 请求日志必须能追溯：
   - 参与下注的有效组
   - 被阀门屏蔽的组
   - 最终唯一号码数
   - 最终总下注额
   - 最终请求条数

### 4.7 结算规则

1. DW3 的最终结算必须以 `getBetChecked` 为准。
2. 系统不得使用 `Confirmbet.betList` 或 `Topbetlist` 作为最终结算依据。
3. 系统不得使用 `MidCode` 作为 DW3 结算匹配主键。
4. 系统必须继续以 `Installments + KeyCode + BettingAmount` 作为主匹配方向。
5. 系统不得自行用赔率重算 `Result` 覆盖平台返回值。
6. 如果某期因为阀门跳过没有真实下注，则该期不得生成 DW3 下注结算记录。

### 4.8 2.0 约束

1. `JND282` 的 DW3 页面、赔率加载、真实下单、`Topbetlist`、`getBetChecked` 已被视为已验证事实。
2. `JND282` 的 DW3 下单参数结构不得再写成 `unsupported`。
3. 即便平台级事实已验证，最终代码上线前仍必须保留一次“2.0 单请求真实下注验收门”。

## 5. 非功能需求

1. 系统不得在热路径中按“每个策略每期扫描最近 N 条开奖记录”实现组阀门。
2. 最近 N 期组阀门在热路径中必须做到固定小规模判断，不得把 `O(N)` 扫描作为正式执行算法。
3. 系统不得在 `key_code_map.py` 中写入 1000 个 DW3 静态映射项。
4. DW3 名称展示必须采用动态规则生成。
5. 系统不得把“简单展开号码后并集去重”误当成最终执行算法。
6. 系统必须支持金额叠加后的单号码最终金额输出。
7. 系统必须具备可重复验证的单元测试、集成测试和实站验收门。
8. 新功能不得破坏既有非 DW3 策略创建、编辑、执行、结算流程。

## 6. 明确排除项

以下内容不属于本次需求，后续如需要必须单独立项：

- DW3 手工选号页
- 任意三位号码自由输入框
- “组合交集单独成一种新玩法”的第三种语义
- 新的 martingale 规则
- 自动回退成分批提交的降级策略
- DW4、四字现、其他定位玩法

## 7. 验收标准

满足以下条件方可视为需求达成：

1. 策略页可以选择 `WEB` 或 `2.0` 的 DW3。
2. 策略页可多选 16 个组合中的任意若干项，并保存最近 `N` 期阀门参数。
3. 保存后后端存的是组合编码与阀门参数，不是 1000 个具体码。
4. 执行时后端能正确生成 `blocked_bs / blocked_oe / effective_bs / effective_oe`。
5. 执行时后端能正确完成同号金额叠加，而不是简单并集去重。
6. 阀门跳过时不会向平台发请求，且 martingale 阶段保持不变。
7. `WEB` 的 DW3 赔率读取必须通过 `settingCode=DW3`。
8. `2.0` 的 DW3 赔率读取必须通过 `settingCode=DW3`。
9. `WEB` 必须通过一次“单请求大包真实下注验收门”。
10. `2.0` 必须通过一次“单请求大包真实下注验收门”。
11. 结算以平台返回 `Result` 为准，且 DW3 匹配不使用 `MidCode`。
