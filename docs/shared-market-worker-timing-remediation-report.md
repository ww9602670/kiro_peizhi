# 共享数据、下注时机与 worker 链路整改报告

落盘时间：2026-05-03

## 当前情况

当前系统已经具备共享数据源、操作者账号 worker、策略下注、结算、心跳和重登等基础链路，但几个关键环节还没有完全收口，导致多策略、多账号、共享账号异常时存在不稳定风险。

1. 下注前仍存在平台倒计时二次校验

   worker 在策略到达下注时间后，仍会在提交投注前调用第三方平台获取当前期号、封盘状态和倒计时，再决定是否允许下注。这样会导致同一个账号多个策略运行时，每组策略下注前都可能额外请求平台倒计时。

   这个行为不符合当前目标。当前目标是：期号、开奖、倒计时主要由共享数据提供；worker 下注时应根据系统内已经记录的期号和倒计时节点执行，不应在每次下注前再依赖平台实时倒计时。

2. 共享数据采集是固定 25 秒轮询，但缺少开奖节点强化刷新

   共享账号目前按固定频率获取期号、开奖数据和倒计时。这个机制可以维持普通刷新，但如果刚好错过开奖切换节点，就可能出现新期开奖数据、期号、封盘倒计时更新不够及时。

   前端会根据拿到的倒计时自行倒计时，但共享源如果没有在开奖后及时刷新，前端展示和 worker 使用的基准数据都会变慢。

3. 共享账号异常时，操作者 worker 会回退获取数据，但边界不够清晰

   当前共享数据异常时，worker 可能使用操作者自己的第三方账号获取期号、倒计时和开奖数据。这个回退方向是正确的，但需要收紧：

   - 回退数据只能服务当前 worker 自己。
   - 不能把操作者账号拉到的数据写回全局共享池。
   - 需要降低回退频率，避免共享组异常时所有 worker 都频繁请求第三方平台。
   - 需要给操作者明确提示，不应让前端空白或无感失败。

4. worker 数据轮询和下注链路仍存在触发频率风险

   worker 自身有常规轮询和慢轮询。正常情况下不应该频繁调用第三方平台数据接口。真正需要高可靠的是下注、结算、心跳和重登，不是每次下注前都重新拉平台倒计时。

   目前最大风险点是：多策略同时运行时，若每个策略组都在下注前执行平台倒计时校验，会增加接口调用频率，也更容易触发平台风控或会话异常。

5. 结算链路有重试，但仍是 worker 主循环内同步执行

   当前结算会在开奖后等待一段时间，然后拉取结算接口，失败后有重试和部分重登能力。这个机制可以完成大多数正常结算，但如果平台短时异常、网络异常、账号会话异常，结算重试会占用 worker 主流程时间。

   现状不一定会永久阻塞下一期下注，但在异常期可能延迟下一期进入下注窗口。

6. 多账号运行架构基本独立，但不是浏览器级真实指纹隔离

   当前系统是按本平台绑定的第三方账号创建独立 worker。每个 worker 有独立会话、心跳、请求锁和登录状态；系统不是用真实浏览器标签页执行，因此不会出现同一浏览器打开多个标签页互相覆盖 cookie 的问题。

   但所有 worker 仍运行在同一服务器出口 IP 下，请求头和网络环境相似。平台如果按 IP、账号行为、请求频率做风控，仍可能受到影响。

7. 错误分类不完整，前端提示不够统一

   当前已经能识别部分赔率变动、封盘、期号不匹配、未知错误，但还没有形成完整错误集。实际平台同类异常可能表现为封盘、停盘、赔率变动、会话异常、账号被顶、余额异常或风控限制。

   另外，部分提示仍可能是英文、乱码或技术化内容，操作者无法直接理解。

## 目标

本次整改目标是把共享数据、下注时机、异常回退、结算和多策略运行链路收口成一套清晰、低频、可解释、可恢复的执行机制。

1. 正常情况下，期号、开奖、倒计时统一由共享账号采集并提供。
2. worker 下注不再每次依赖第三方平台实时倒计时，而是根据系统内记录的当前期号和封盘倒计时节点执行。
3. 共享账号异常时，worker 才启动自己的低频数据回退链路，频率固定为 80 秒一次。
4. 共享异常时，前端必须明确提示：数据更新变慢，可能影响投注，请联系管理员处理。日志编号：SHARED-002。
5. worker 回退获取的数据只给当前 worker 使用，不写入全局共享池。
6. 多策略同账号运行时，下注时机自动错开；时机不足时给操作者明确中文提示。
7. 多账号同操作者运行时，各账号 worker 独立，互不共享登录会话。
8. 下注失败后再执行账号自检，不在下注前增加不必要的平台探测。
9. 结算失败要有重试、重登、重新拉取能力，并且不能让异常提示停留在英文或乱码。
10. 管理员和操作者都能看到明确、简短、可追踪的中文异常提示，详细过程保留到后端日志。

## 需要修改的模块和内容

### 1. worker 下注时机链路

涉及模块：

- `backend/app/engine/worker.py`
- `backend/app/engine/poller.py`
- `backend/app/engine/shared_market_runtime.py`
- `backend/app/api/lottery.py`

修改内容：

1. 移除正常下注前对第三方平台倒计时的二次强依赖校验。
2. worker 到达下注时间后，使用系统内当前期号、封盘截止时间和本地递减倒计时判断是否下注。
3. 保留必要安全校验，例如期号必须存在、共享快照不能过期过久、当前状态不能是明确停盘。
4. 如果下注接口返回失败，再进入后置诊断链路：
   - 先检测心跳。
   - 再检测账号盘口状态。
   - 再根据错误内容归类为封盘、停盘、会话异常、赔率变动、余额异常、风控或未知异常。
5. 若平台明确返回停盘，则自动停止对应策略或账号 worker，并产生中文告警。
6. 若多次返回封盘，则上报异常日志，提示管理员检查采集时机或盘口状态。

整改目的：

worker 不再因为每次下注前额外探测平台倒计时而提高请求频率，也避免共享账号采集稍慢时影响下注时机判断。

### 2. 共享数据采集链路

涉及模块：

- `backend/app/engine/shared_market_runtime.py`
- `backend/app/engine/poller.py`
- `backend/app/main.py`
- `backend/app/api/admin.py`
- `backend/app/api/lottery.py`

修改内容：

1. 正常共享采集频率保持 25 秒一次。
2. 增加开奖节点额外刷新：
   - 当共享快照里的开奖倒计时到 0 后，不立即认定开奖结果已经可用。
   - 按最终专项刷新节奏执行：归零后 10 秒首刷；未拿到新数据时再按 10 秒、10 秒、5 秒、3 秒、1 秒继续刷新；第 6 次仍未拿到时提示前端 `开奖数据暂未获取，10秒后再次刷新`，之后每 10 秒继续刷新，直到拿到新开奖数据或检测到停盘。
   - 拉到新期号或新开奖数据后，以这次成功采集时间作为新的 25 秒周期起点。
3. 共享账号异常时，标记共享源不可用，并写入 admin 异常。
4. 共享源异常时，操作者前端提示：

   `数据更新变慢，可能影响投注，请联系管理员处理。日志编号：SHARED-002。`

5. 共享源异常时，worker 才允许启动自己的数据回退链路。
6. worker 回退获取期号、开奖、倒计时的频率固定为 80 秒一次。
7. worker 回退数据只用于当前 worker，不允许写回共享池。
8. 系统启动顺序调整为：先启动共享采集器，再恢复已启动的 worker，避免 worker 先于共享采集器触发大量本地回退。

整改目的：

共享账号正常时，所有操作者都使用共享数据；共享账号异常时，操作者不会空白，worker 也不会高频补采数据。

### 3. 前端倒计时和提示展示

涉及模块：

- `frontend/src/hooks/useLotteryCountdown.ts`
- `frontend/src/components/CountdownDisplay.tsx`
- 操作者策略页、开奖展示页、告警展示组件

修改内容：

1. 前端继续根据后端快照进行本地倒计时。
2. worker 和前端不直接互相读取倒计时，而是共同使用后端共享快照里的同一组期号、倒计时和截止时间。
3. 当前封盘倒计时为 0 时，状态显示为：封盘中。
4. 封盘倒计时和开奖倒计时都为 0 时，状态显示为：等待开奖。
5. 所有操作者关键提示改为弹窗或明显提示，包括：
   - 账号会话异常。
   - 数据更新变慢。
   - 策略无法下注。
   - 策略过多导致下注时机不足。
   - 平台停盘。
   - 余额接口异常。
6. 普通同步成功、普通刷新、非阻塞后台重试不弹窗，只保留日志或轻提示。

整改目的：

操作者能明确知道系统当前是否能正常下注，不能再出现前端空白、英文提示、乱码提示或失败无感。

### 4. 策略下注时机错开

涉及模块：

- `backend/app/utils/strategy_timing.py`
- `backend/app/api/strategies.py`
- `frontend/src/pages/operator/StrategyForm.tsx`

修改内容：

1. 默认下注时机保持 88 秒。
2. 允许下注时机区间为 10 到 100 秒。
3. 同一账号、同一玩法方向的多策略，默认至少错开 20 秒。
4. 如果系统发现当前账号相同玩法策略过多，已经没有可用下注时机，需要阻止继续创建或启动，并提示：

   `当前账号相同玩法策略过多，已无可用下注时机，继续运行可能引发风控或下注失败，请减少策略或调整下注玩法。`

5. 操作者手动设置较低下注时机时，需要弹窗提示存在临近封盘失败风险。

整改目的：

同账号多策略运行时尽量错开请求，降低同一时间集中投注触发风控的风险。

### 5. 多账号和重复第三方账号绑定

涉及模块：

- `backend/app/engine/manager.py`
- `backend/app/engine/session_runtime.py`
- `backend/app/api/platform_accounts.py`
- 操作者账号绑定页

修改内容：

1. 保持一个本平台绑定账号对应一个独立 worker。
2. 每个 worker 独立登录、独立心跳、独立请求锁、独立会话。
3. 同一操作者绑定多个第三方账号时，不共享登录态。
4. 若系统发现同一个第三方账号已经被其他本平台账号绑定，不做硬性拦截，但必须提示：

   `该第三方投注账号已被其他操作者绑定。如继续绑定，请先修改第三方账号密码，避免运行策略时互相顶号。`

5. 如同一个第三方账号已在别处真实运行，再次启动真实策略时给高风险提示。

整改目的：

保证同一操作者多账号策略可以并行运行，同时降低重复绑定同一个第三方账号导致互相顶号的风险。

### 6. 下注失败后的错误归类和自恢复

涉及模块：

- `backend/app/engine/adapters/base.py`
- `backend/app/engine/adapters/jnd.py`
- `backend/app/engine/executor.py`
- `backend/app/engine/session_runtime.py`
- `backend/app/engine/alert.py`

修改内容：

1. 建立统一错误分类：
   - 赔率变动
   - 封盘
   - 停盘
   - 期号不匹配
   - 会话异常
   - 账号被顶
   - 余额异常
   - 平台风控或限频
   - 网络异常
   - 未知异常
2. 赔率变动只在当前策略实际使用的盘口和玩法发生变动时提醒，避免无关盘口的赔率变动污染操作者告警。
3. 如果下注失败是会话异常或疑似账号被顶，执行重登后再按规则重试。
4. 如果余额接口异常，先检测心跳，再进入重登和重拉余额链路，不能直接把余额误判为 0。
5. 所有前端提示必须是简短中文，并带日志编号；详细错误、平台返回内容、请求阶段写入后端日志。

整改目的：

减少无用告警，让真正影响下注的异常可解释、可追踪、可恢复。

### 7. 结算链路

涉及模块：

- `backend/app/engine/settlement.py`
- `backend/app/engine/worker.py`
- `backend/app/engine/session_runtime.py`

修改内容：

1. 保留开奖后等待再拉结算的机制。
2. 结算失败时执行重试。
3. 如果结算失败疑似会话异常，先心跳检测，再重登，再重新拉结算。
4. 结算失败只影响当前待结算记录，不应直接导致下一期不能下注。
5. 若连续结算失败，前端显示中文告警，管理员日志保留详细接口返回。
6. 结算获取必须与下注执行拆成独立分支；结算失败只能让当前订单进入 `settlement_pending` 或补偿队列，不能拖住下一期下注。
7. 同一第三方账号的结算请求按账号维度串行聚合，不允许多个策略各自并发拉取结算。

整改目的：

提高结算恢复能力，避免一次结算异常扩大成策略停止或下一期无法下注。

## 风险点

1. 平台错误返回格式不稳定

   同一个真实原因可能返回不同文案或不同字段，例如封盘、停盘、会话异常、赔率变动、账号被顶可能混在一起。错误分类需要持续补充真实样本。

2. 共享账号异常时 worker 仍会增加平台请求

   虽然回退频率会降低到 80 秒一次，但如果同时运行大量 worker，平台请求量仍会上升。需要管理员尽快修复共享账号，不能长期依赖 worker 回退。

3. 多账号共享同一出口 IP

   当前 worker 会话独立，但不是浏览器级指纹隔离。大量账号同机运行时，仍可能被平台按 IP 或行为频率识别。

4. 下注时机过密仍可能触发风控

   即使系统自动错开 20 秒，如果同一账号策略数量过多或玩法重复过多，仍可能集中请求。需要在创建和启动策略时提前阻止。

5. 取消下注前平台倒计时强校验后，更依赖共享快照准确性

   这要求共享采集、开奖节点刷新、前端倒计时和 worker 快照过期判断必须可靠。否则可能出现使用过期快照下注的风险。

6. 结算仍可能被平台延迟影响

   平台结算数据本身可能延迟返回。即使系统重试和重登正常，也可能出现 `settlement_pending` 的等待状态；只有超过最长等待或明确不可恢复时才应标记 `settle_failed`，并保留补偿更新入口。

## 整改后实现什么

整改完成后，系统应达到以下效果：

1. 共享账号正常时，操作者前端、worker、策略都使用同一套共享期号、开奖和倒计时数据。
2. worker 按系统记录的下注时机执行，不再每次下注前额外拉平台倒计时。
3. 多策略同账号运行时，下注时间自动错开；错不开时提前提示，不让操作者继续堆策略。
4. 共享账号异常时，操作者看到明确提示，不会空白；worker 以 80 秒一次的低频方式临时自取数据。
5. worker 自取数据不会污染全局共享池。
6. 每期开奖切换后，共享采集会额外刷新一次，提升新期号和开奖数据同步速度。
7. 下注失败后才执行账号自检、心跳、盘口状态确认和重登，减少无意义请求。
8. 余额接口异常不会再直接误判余额为 0，而是先走心跳和重登链路。
9. 无关盘口赔率变动不会再污染当前策略告警。
10. 操作者看到的是简短中文提示，维护人员可以通过日志编号查看后端详细过程。

## 验收标准

1. 启动共享账号后，操作者前端能持续看到期号、开奖数据和倒计时。
2. 共享采集正常频率为 25 秒；开奖倒计时结束后按 10 秒、10 秒、10 秒、5 秒、3 秒、1 秒的专项节奏刷新，之后每 10 秒继续刷新，直到拿到新开奖数据或检测到停盘。
3. 关闭或破坏共享账号后，操作者前端出现 `SHARED-002` 提示，worker 每 80 秒以内最多独立获取一次开奖相关数据。
4. worker 下注前不再调用平台倒计时接口做常规二次确认。
5. 同一账号创建多个相同玩法策略时，下注时机自动错开；无可用时机时出现中文阻止提示。
6. 同一操作者多个第三方账号同时运行时，各 worker 会话独立，互不顶号。
7. 下注失败时，系统能归类错误并给出中文告警。
8. 结算失败后能重试、重登、重拉；失败记录不会阻塞下一期正常下注。
9. 前端不存在英文、乱码或不明显的关键告警。
10. 管理员端能看到共享账号异常、worker 回退、下注失败和结算失败的详细日志编号。

## 执行约束

1. 不允许新增无关功能。
2. 不允许扩大策略算法范围。
3. 不允许修改现有马丁、平注、AI 推荐策略的选号规则。
4. 不允许把 worker 回退数据写入全局共享池。
5. 不允许在正常下注前恢复平台倒计时强校验。
6. 不允许把重复第三方账号绑定改成硬拦截，只能提示风险。
7. 不允许改变下注、结算、心跳频率，除非本报告明确要求。
8. 如执行中发现当前代码结构与本报告假设冲突，应停止执行并上报，不得自行扩展替代方案。

## 第一阶段新增整改项

### 1. 运行中账号仍提示重新验证

当前现象：

操作者账号的策略正在正常执行，worker 也能继续下注和结算，但操作者在重新修改策略或新建策略时，前端提示需要先执行登录或验证。

已查证结果：

1. 当前代码中账号验证有效期为 30 分钟。
2. 验证过期后，策略创建和策略编辑接口会把该账号视为 `verification_stale`，从而拦截操作。
3. 服务器日志显示，北京时间 2026-05-03 00:20 至 01:30 期间，`shun666 / yi6666 / account_id=29` 仍在持续成功下注和结算。
4. 数据库中该账号验证记录存在 `ttl_expired`：
   - 00:18:37 完成的验证，在 00:49:11 被标记过期。
   - 01:30:52 完成的验证，在 02:02:41 被标记过期。
5. 因此这里不是 worker 会话掉线导致，而是“账号验证结果过期”与“worker 实际在线运行”之间的状态口径不一致。

根因：

账号验证结果被设计成短时有效凭证，但策略运行使用的是 worker 自己维护的登录会话。worker 运行正常时，前端和策略接口仍因为验证 TTL 过期要求操作者手动重新验证，造成“实际能下注，但编辑或新建策略被拦”的误判。

需要修复：

1. 拆分两个状态：
   - 平台会话状态：用于判断 worker 是否还能下注、心跳是否正常、是否需要重登。
   - 账号能力验证状态：用于判断该账号支持哪些盘口、赔率和策略类型。
2. 验证记录因为 TTL 过期时，不应直接等同于账号掉线。
3. 如果账号平台会话仍是 online，且最近一次能力验证结果支持当前策略平台，应允许策略编辑和新建继续执行。
4. 如果确实需要刷新能力验证，后端应优先使用当前 session_runtime 做后台刷新，而不是要求操作者手动重新登录。
5. 只有在会话状态为 login_error、手动登出、账号密码或平台链接变化、能力验证从未成功过时，才提示操作者重新验证。
6. 前端提示必须区分：
   - “账号会话异常，请重新验证。”
   - “账号能力信息过期，系统正在刷新，请稍后重试。”
   - “当前账号未开通该盘口或策略。”

整改目标：

运行中的真实投注账号如果 worker 会话正常，不应因为 30 分钟验证 TTL 到期而影响策略编辑或新建。验证 TTL 只用于后台刷新能力信息，不作为直接判定掉线的依据。

### 1.1 策略创建、编辑、启动不再由绑定账号验证状态主导

最新确认口径：

绑定账号完成后，该账号信息只作为 worker 登录第三方平台的资料来源。策略是否能创建、编辑、启动和恢复运行，不应再由绑定账号的短期验证状态主导。

当前代码问题：

1. 创建策略时会检查账号是否存在有效验证结果。
2. 编辑策略时如果变更平台类型，也会检查有效验证结果。
3. 启动策略时会检查 `verification_stale` 和 `effective_verification_run_id`。
4. 服务重启后恢复运行中策略时，也会因为验证过期跳过 worker 恢复。
5. 这些检查会导致：worker 明明可以自己登录并执行下注，但策略创建、编辑、启动或重启恢复却被“请先验证账号”拦住。

需要修改：

1. 创建策略时只校验：
   - 账号属于当前操作者。
   - 策略类型已被管理员授权。
   - 策略参数合法。
   - 玩法、金额、止盈止损、下注时机合法。
2. 创建策略时不再校验：
   - `verification_stale`
   - `effective_verification_run_id`
   - `allowed_strategy_platform_types`
   - 绑定账号当前是否 online。
3. 编辑策略时同样不再因为验证过期阻断。
4. 启动策略时由 worker 自己执行登录链路：
   - 登录成功，策略进入运行。
   - 登录失败，策略启动失败并显示明确中文提示。
   - 登录失败不应伪装成“请先重新验证绑定账号”。
5. 服务重启恢复 worker 时，不再因为验证结果过期跳过恢复。只要策略状态是 running，账号资料存在，就尝试恢复 worker。
6. 绑定账号的重新验证功能保留，但只用于：
   - 首次绑定后确认账号密码和平台链接可用。
   - 操作者主动刷新余额、赔率或盘口能力。
   - 账号密码、平台链接变更后重新确认。
   - 管理员或操作者主动排查账号异常。
7. 绑定账号验证结果不再作为策略创建、编辑、启动、恢复运行的硬门槛。

整改后的判断口径：

1. 策略创建阶段：看本系统账号权限和策略参数。
2. 策略启动阶段：看 worker 能否登录第三方平台。
3. 策略运行阶段：看 worker 心跳、下注返回、结算返回和重登结果。
4. 账号页验证状态：只作为账号资料健康度提示，不再主导策略生命周期。

### 1.2 第三方账号被顶后的 worker 重登机制

当前代码查证：

1. worker 启动时会执行自己的登录链路，不依赖账号页重新验证。
2. 运行中平台接口如果抛出 `RemoteLoginRequired`，worker 会进入 recover 链路。
3. recover 链路会先检测心跳；心跳仍正常时，不强制重登。
4. 心跳异常时，worker 会执行重连或重新登录。
5. 心跳频率当前为 10 秒一次，连续 3 次失败后触发重连。
6. 登录失败有退避：
   - 第 1 次失败后等 30 秒。
   - 第 2 次失败后等 60 秒。
   - 第 3 次失败后等 120 秒。
   - 第 3 次失败后还会额外暂停 600 秒。
   - 最多尝试 5 次。
7. worker 主循环异常也有退避重启：
   - 5 秒
   - 10 秒
   - 30 秒
   - 最多连续 5 次失败后进入终止错误处理。

当前不足：

1. 退避机制已经存在，但提示文案仍有英文或技术化内容。
2. 被顶号后如果重登成功，worker 会继续执行策略。
3. 被顶号后如果连续重登失败，worker 会停止并把策略标记为错误。
4. 当前没有专门的“被顶号”中文分类提示，很多情况会混入 session_lost、Remote login 或 login_fail。
5. 如果平台返回的被顶号信息没有被适配器识别为 `RemoteLoginRequired`，可能会被归为普通失败或未知错误。

需要修改：

1. 增加“账号被顶”错误分类。
2. 平台返回疑似异地登录、重复登录、session 失效、State 异常时，统一归类到会话异常或账号被顶。
3. 被顶号后先执行 worker 自己的重登链路，不要求操作者去账号页重新验证。
4. 重登成功后，策略继续运行。
5. 重登失败后，策略停止或进入错误状态，并提示：

   `第三方账号会话异常，系统自动重登失败，策略已暂停。请确认账号是否在其他地方登录。日志编号：SESSION-002。`

6. 对连续重登失败保持退避，避免高频反复登录触发风控。

整改目标：

第三方账号被顶后，worker 先自动恢复；恢复成功继续执行，恢复失败才提醒操作者。账号页重新验证不再介入运行中策略的自动恢复链路。

### 2. 共享账号开奖节点刷新机制补全

当前情况：

1. 共享采集器目前是固定 25 秒获取一次期号、开奖数据和倒计时。
2. 前端倒计时归零后，会在本地等待 30 秒再重新请求一次后端数据。
3. worker 当前在结算阶段是先等待开奖倒计时归零，再额外等待 `settlement_wait_seconds`，默认 30 秒，然后调用 `_fetch_settlement_data()`。
4. `_fetch_settlement_data()` 当前最多重试 6 次，每次间隔 5 秒。
5. worker 不是直接去找共享账号登录取数据，而是通过 poller 读取共享快照；如果共享快照缺失、过期或异常，当前代码可能回退到操作者账号本地拉取数据。
6. 当前共享采集器没有“开奖倒计时结束后按阶梯频率刷新开奖结果”的完整状态机。

需要补齐的完整机制：

1. 每次共享账号成功采集后，后端保存以下基准信息：
   - 当前期号
   - 上期开奖结果
   - 封盘倒计时
   - 开奖倒计时
   - 采集时间
   - 根据开奖倒计时计算出的预计开奖完成时间
2. 正常阶段继续每 25 秒采集一次。
3. 当系统根据共享快照判断开奖倒计时已经归零后，不应立刻认定新开奖数据已经可用。
4. 第一次开奖结果专项刷新应安排在“开奖倒计时归零后 10 秒”。
5. 如果这次没有拿到新期开奖结果，或者拿到的 `pre_issue` 不是预期上一期：
   - 标记共享状态为 `draw_pending`。
   - 暂停与本次开奖结果专项刷新重叠的普通 25 秒采集，避免并发重复请求。
   - 按 10 秒、10 秒、5 秒、3 秒、1 秒的间隔继续执行第 2 至第 6 次专项刷新。
   - 第 6 次仍未拿到新数据时，前端提示：`开奖数据暂未获取，10秒后再次刷新`。
   - 之后以 10 秒一次继续刷新，直到拿到新开奖数据或检测到平台停盘。
6. 如果任意一次拿到正确新期开奖结果或新期号：
   - 写入共享快照。
   - 清除 `draw_pending`。
   - 从这次成功采集时间重新开始计算下一轮 25 秒普通采集周期。
7. 如果检测到平台停盘：
   - 标记共享状态为 `market_closed`。
   - 停止本期开奖专项重复刷新。
   - 前端提示：`当前处于停盘`。
   - worker 不再等待新期开奖数据，但仍必须继续执行结算数据获取链路。
8. 只有当共享状态进入异常、过期或不可用时，worker 才允许启动自己的 80 秒低频回退采集。
9. worker 回退采集只服务当前 worker，不写入全局共享池。

worker 在共享正常时如何拿开奖数据：

1. worker 不直接登录共享账号。
2. worker 读取的是后端共享快照。
3. 正常情况下，worker 从开奖倒计时归零后的第 11 秒开始，每 5 秒读取一次本地共享快照里的上期开奖结果。
4. 如果共享快照已经有正确结果，直接进入结算。
5. 如果共享快照正在 `draw_pending` 或 `draw_wait_retry`，worker 等待共享刷新结果，不主动改用操作者账号高频拉取。
6. 只有共享状态明确进入 `shared_error`、`shared_stale` 或共享采集器不可用时，worker 才进入 80 秒一次的本地回退采集。

整改目标：

开奖节点不再依赖盲目 25 秒轮询，也不让 worker 在共享正常时重复调用平台开奖接口。共享账号负责开奖节点专项刷新，worker 只消费共享快照。

### 3. 当前问题的结论性回答

问题：共享账号能正常提供数据时，worker 是不是在开奖倒计时结束后去找共享账号获取数据？频率是什么？

当前实际链路不是这个精确逻辑。

当前 worker 是在开奖倒计时结束后，再等待默认 30 秒，然后调用 `_fetch_settlement_data()`。该方法通过 poller 获取当前开奖快照。poller 优先读取共享快照；如果共享快照新鲜，就使用共享数据；如果共享快照缺失、过期或异常，当前代码可能回退到操作者账号本地拉取。当前重试为最多 6 次，每次间隔 5 秒。

当前共享账号自己并没有“开奖倒计时结束 30 秒后专项刷新开奖数据”的明确机制，它只是按 25 秒固定采集。前端倒计时归零后 30 秒刷新，是前端自己的刷新逻辑，不等于共享账号后端专项采集。

因此第一阶段需要把后端共享账号改成明确的开奖节点刷新机制：开奖倒计时归零后 10 秒第一次专项刷新，然后按 10 秒、10 秒、5 秒、3 秒、1 秒继续刷新；第 6 次仍未拿到新数据则提示前端 10 秒后再次刷新，并以 10 秒频率继续刷新直到拿到数据。成功后重置为 25 秒普通采集周期；检测到停盘则停止本期开奖专项刷新。

## 补充风险点

1. 如果只放宽验证 TTL，而不检查账号会话状态，可能让真正掉线账号继续创建策略。因此必须以平台 session 状态和最近能力验证结果共同判断。
2. 共享开奖专项刷新如果重试间隔太短，会增加共享账号请求频率；如果间隔太长，会导致前端开奖展示变慢。最终采用开奖倒计时归零后 10 秒首刷，之后按 10 秒、10 秒、5 秒、3 秒、1 秒继续刷新，第 6 次后以 10 秒一次持续刷新，直到拿到新数据或检测到停盘。
3. `draw_pending` 和 `draw_wait_retry` 属于开奖过程状态，不应直接触发 worker 本地回退；只有共享状态进入 `shared_error`、`shared_stale` 或明确不可用时，worker 才进入 80 秒低频回退。
4. H5 页面优化不得改变 Web 端布局，不得影响现有策略创建和下注功能。

## 2026-05-03 二次审查补充：开奖数据、共享读取和结算时机

本节用于补齐前文仍不够硬的执行边界，避免开发时把“worker 读取共享快照”误实现成“worker 继续请求第三方平台”。

### 1. 共享账号采集平台数据的频率

结论：

共享账号正常时，只有共享采集器负责请求第三方平台的开奖、期号和倒计时接口。worker 和前端都不直接请求第三方平台获取开奖倒计时数据。

建议频率：

1. 普通阶段：共享采集器每 25 秒请求一次第三方平台。
2. 每次成功采集后，后端保存：
   - 当前期号
   - 上期开奖结果
   - 封盘倒计时
   - 开奖倒计时
   - 采集时间
   - 预计开奖完成时间
   - 下一次开奖专项刷新时间
3. 开奖倒计时归零后，不立刻认定开奖结果已经可用。
4. 为了让前端更及时看到新开奖数据，专项刷新从“开奖倒计时归零后 10 秒”开始。
5. 如果 10 秒首刷没有拿到新期开奖结果，则按以下间隔继续刷新：
   - 第 2 次：间隔 10 秒。
   - 第 3 次：间隔 10 秒。
   - 第 4 次：间隔 5 秒。
   - 第 5 次：间隔 3 秒。
   - 第 6 次：间隔 1 秒。
6. 第 6 次仍未拿到新数据时，前端提示：`开奖数据暂未获取，10秒后再次刷新`。
7. 之后以 10 秒一次继续刷新，直到获取到新开奖数据。
8. 如果刷新期间检测到平台停盘：
   - 停止本期开奖专项重复刷新。
   - 标记共享状态为 `market_closed`。
   - 前端提示：`当前处于停盘`。
9. 专项刷新期间暂停与它重叠的普通 25 秒采集，避免同一共享账号并发请求平台。
10. 任意一次拿到正确新期开奖结果或新期号后：
   - 写入共享快照。
   - 清除 `draw_pending`。
   - 从成功采集时间重新计算下一轮 25 秒普通采集。

说明：

10 秒首刷可以让前端更早进入“等待开奖 / 正在获取开奖数据”的可感知状态。前 6 次属于开奖节点专项刷新，由共享账号统一执行，不允许每个 worker 单独请求第三方平台。第 6 次后转为 10 秒一次的持续刷新，直到拿到新数据或检测到停盘。

### 2. worker 读取共享数据的频率

结论：

worker 可以较高频读取“本地共享快照”，但不能把读取本地快照变成请求第三方平台。

执行规则：

1. worker 正常运行时，只读取后端共享快照或内存缓存。
2. worker 读取共享快照的频率可以跟随自身循环，例如 5 秒一次，因为这是本地读，不是平台请求。
3. worker 在共享账号正常时，不允许调用操作者账号去补采开奖、期号、倒计时。
4. worker 在共享快照为 `draw_pending` 时，应等待共享采集器专项刷新，不主动回退操作者账号。
5. worker 只有在共享状态进入以下情况时，才允许启动本地回退：
   - `shared_error`
   - `shared_stale`
   - 共享采集器明确不可用或共享快照已经超过可用新鲜度
6. worker 本地回退频率固定为 80 秒一次。
7. worker 回退采集的数据只服务当前 worker，不写入共享池。
8. worker 回退采集期间，前端提示：

   `数据更新变慢，可能影响投注，请联系管理员处理。日志编号：SHARED-002。`

需要修改的关键点：

当前 `resolve_install()` 在共享快照缺失、过期或异常时可能立即调用操作者账号本地拉取，并写回共享池。整改后必须改成：

1. 共享正常或 `draw_pending`：只返回共享快照状态，不触发操作者账号本地采集。
2. 共享异常：按 80 秒节流允许当前 worker 本地采集。
3. 本地采集结果不得写入全局共享池。

### 3. 前端获取新开奖数据的时机

结论：

前端需要及时看到新开奖数据，但前端也不直接请求第三方平台。前端只请求本系统后端。

建议机制：

1. 前端拿到后端共享快照后，本地每秒倒计时。
2. 封盘倒计时为 0 时显示：封盘中。
3. 封盘倒计时和开奖倒计时都为 0 时显示：等待开奖。
4. 开奖倒计时归零后，前端不应固定等待 30 秒才请求。
5. 前端应根据后端返回的 `next_draw_refresh_at` 或 `draw_pending` 状态决定刷新。
6. 如果没有新增字段，前端默认在开奖倒计时归零后 10 秒请求一次后端。
7. 如果后端返回 `draw_pending` 或期号未切换，前端每 5 秒请求一次后端，直到：
   - 新期号出现；
   - 上期开奖结果更新；
   - 后端返回 `开奖数据暂未获取，10秒后再次刷新`；
   - 后端返回停盘状态。
8. 后端返回 `draw_wait_retry` 或 `next_draw_retry_at` 后，前端不再继续 5 秒轮询，应按后端给出的下一次刷新时间请求；没有字段时默认 10 秒后请求。

整改目标：

正常情况下，前端应在开奖倒计时归零后尽快进入可感知刷新状态；平台本身延迟时，前端显示等待开奖、开奖数据暂未获取或当前停盘，而不是空白。

### 4. worker 拉取结算的时机

当前情况：

worker 当前是在本期下注后，等待开奖倒计时归零，再额外等待默认 30 秒，然后调用 `_fetch_settlement_data()`。当前 `_fetch_settlement_data()` 最多重试 6 次，每次 5 秒。

审查结论：

这个时机在平台正常时基本可用，但不够稳妥。主要问题是：

1. 如果共享开奖结果专项刷新还在 `draw_pending`，worker 可能过早判定结算数据缺失。
2. 如果平台开奖结果或结算接口延迟超过 30 秒，当前逻辑可能过早进入 `settle_failed`。
3. 结算仍在 worker 主循环内同步执行，异常情况下可能拖慢下一期下注。

建议整改：

1. 开奖结果获取和结算数据获取必须拆成两个独立分支。
2. 开奖结果没有及时获取到，不能阻塞结算数据获取。
3. 当共享数据传来停盘信号时，worker 仍需要执行结算数据获取。
4. worker 结算首取时间改为“开奖倒计时归零后 20 秒”。
5. 结算获取退避间隔采用：
   - 首次：开奖倒计时归零后 20 秒。
   - 第 2 次：间隔 10 秒。
   - 第 3 次：间隔 5 秒。
   - 第 4 次：间隔 8 秒。
   - 第 5 次及之后：间隔 10 秒。
6. 结算数据最多等待 10 分钟。
7. 10 分钟内拿到结算数据，立即完成结算、更新盈亏和余额。
8. 10 分钟内仍无有效结算数据，才标记为 `settle_failed` 并发中文告警。
9. 结算获取应独立运行，不能阻塞下一期下注。
10. 如果拉取第三方结算接口时出现会话异常，走 worker session_runtime 重登链路；重登成功后继续结算，重登失败才告警。
11. worker 如果需要从共享快照读取开奖结果，可以从开奖倒计时归零后的第 11 秒开始，每 5 秒读取一次本地共享快照；这个读取不等于请求第三方平台。

整改目标：

1. 正常情况下，结算在开奖后 20 至 60 秒内完成。
2. 平台延迟时，不误判为最终结算失败。
3. 结算异常不影响下一期正常下注。
4. 前端能看到“待结算 / 结算中 / 结算失败”的明确中文状态。

### 5. 本轮审查后的推荐最终时机

推荐采用以下最终时机：

1. 共享普通采集：每 25 秒一次。
2. 共享开奖专项首刷：开奖倒计时归零后 10 秒。
3. 共享开奖专项重试：第 2 次间隔 10 秒，第 3 次间隔 10 秒，第 4 次间隔 5 秒，第 5 次间隔 3 秒，第 6 次间隔 1 秒。
4. 第 6 次仍未拿到新数据：前端提示 `开奖数据暂未获取，10秒后再次刷新`，共享账号之后每 10 秒继续刷新，直到拿到数据或检测到停盘。
5. 检测到停盘：停止本期开奖专项刷新，前端提示 `当前处于停盘`。
6. 前端开奖后刷新：开奖倒计时归零后 10 秒；如 `draw_pending`，每 5 秒请求本系统后端；如进入 `draw_wait_retry`，按 `next_draw_retry_at` 或默认 10 秒请求。
7. worker 正常读共享快照：可随 worker 循环 5 秒读取一次，但只能读本地快照。
8. worker 从共享快照读取开奖结果：开奖倒计时归零后第 11 秒开始，每 5 秒读一次本地共享快照。
9. worker 本地回退采集：共享异常后最多 80 秒一次。
10. worker 结算首取：开奖倒计时归零后 20 秒。
11. worker 结算退避：20 秒首取后，按 10 秒、5 秒、8 秒、之后每 10 秒继续获取。
12. worker 结算最长等待：10 分钟。
13. 开奖结果获取和结算数据获取是两个独立分支，开奖数据延迟或停盘信号不能阻塞结算获取。

### 6. 同一共享组并发和 worker 状态接收

同一共享组并发是什么意思：

同一个第三方平台可能存在多个备用网址，例如不同操作者绑定了不同链接，但这些链接实际属于同一个投注平台。系统会把这些链接归到同一个共享组。这个共享组通常只需要一个共享账号负责采集开奖、期号和倒计时。

并发风险指的是：同一共享组在同一时间被多个入口触发刷新，导致同一个共享账号同时向第三方平台发起多次请求。

可能触发并发的入口：

1. 普通 25 秒采集循环。
2. 开奖倒计时归零后的专项刷新。
3. 管理员手动重新检测共享链接。
4. 多个 worker 同时发现共享快照过期后尝试触发刷新。
5. 共享组刚启动或服务重启恢复时，多个账号同时触发共享采集器初始化。

整改约束：

1. 同一个 `shared_group_id` 必须有单飞锁。
2. 同一时间同一共享组只能有一个平台采集请求在执行。
3. 开奖专项刷新执行期间，普通 25 秒采集必须跳过或顺延。
4. 管理员手动检测不能打断正在执行的开奖专项刷新，应排队或复用当前刷新结果。
5. worker 不允许直接触发同一共享组的第三方平台采集；worker 只能读取共享快照或等待共享组下一次刷新。
6. 共享组刷新成功后，所有前端和 worker 都消费同一份快照。

worker 必须接收的共享状态：

1. `shared_ok`：共享数据正常。
2. `draw_pending`：开奖倒计时已结束，正在等待新开奖数据。
3. `draw_wait_retry`：开奖数据暂未获取，10 秒后再次刷新。
4. `market_closed`：当前处于停盘。
5. `shared_error`：共享账号异常。
6. `shared_stale`：共享快照过期。

worker 接收到不同状态后的动作：

1. `shared_ok`
   - 正常读取共享快照。
   - 正常执行下注时机判断。
   - 正常进入结算分支。

2. `draw_pending`
   - 不调用操作者账号去补采开奖数据。
   - 从开奖倒计时归零后的第 11 秒开始，每 5 秒读取一次本地共享快照。
   - 不把“暂未开奖”判定为结算失败。
   - 结算分支仍按独立节奏执行。

3. `draw_wait_retry`
   - 前端显示：`开奖数据暂未获取，10秒后再次刷新`。
   - worker 不再以 5 秒频率持续追问共享数据。
   - worker 应按照共享快照给出的下一次刷新时间，或默认 10 秒后再读取共享快照。
   - 结算分支继续独立执行，不受该状态阻塞。

4. `market_closed`
   - 前端显示：`当前处于停盘`。
   - worker 停止本期开奖数据等待分支，不再持续向共享数据端索要本期开奖数据。
   - worker 不再为停盘期生成新的下注信号。
   - worker 仍必须执行结算数据获取，不能因为停盘而跳过已有订单结算。
   - 状态变化只告警一次，避免重复刷屏。

5. `shared_error` 或 `shared_stale`
   - 前端显示：`数据更新变慢，可能影响投注，请联系管理员处理。日志编号：SHARED-002。`
   - worker 才允许进入本地回退采集。
   - 本地回退采集频率最多 80 秒一次。
   - 本地回退结果只服务当前 worker，不写入共享池。

展示要求：

1. 操作者前端必须能看到共享状态提示。
2. worker 侧必须把接收到的共享状态写入运行日志。
3. 策略或账号状态页应能区分：
   - 正常运行
   - 等待开奖数据
   - 当前停盘
   - 共享数据异常
   - 结算中
4. 停盘、共享异常、结算失败必须有中文提示和日志编号。
5. `draw_pending` 和 `draw_wait_retry` 属于过程状态，不应直接升级为失败告警。

### 7. 结算请求串行和错峰约束

新增约束：

1. 同一个第三方账号的结算请求必须串行执行。
2. 同一个第三方账号不能同时执行多个结算接口请求。
3. 多个策略同账号运行时，结算应按账号维度聚合处理，不按策略各自并发拉取。
4. 如果多个账号同时到达结算节点，可以增加 0 至 3 秒轻微错峰。
5. 错峰只用于避免大量账号同一秒集中请求平台，不改变结算首取时间和最长等待时间。
6. 结算串行锁不能阻塞下一期下注；下注和结算应使用独立分支。

整改目标：

1. 避免开奖后 20 秒所有策略或所有账号同时打结算接口。
2. 避免同账号多策略重复拉取结算数据。
3. 降低平台风控风险。
4. 保证结算异常不会拖住下一期下注。

### 8. 完整复审后仍需补齐的工程细节和风险

本节是对全文再次复审后的补充，用于避免执行 agent 在开发时只按描述实现频率，却漏掉状态契约、幂等和异常恢复。

#### 8.1 共享快照字段契约需要明确

共享快照不应只保存期号和倒计时，还需要保存可被前端、worker 和管理员共同理解的状态字段：

1. `shared_group_id`：共享组标识。
2. `market_data_state`：`shared_ok`、`shared_error`、`shared_stale`、`market_closed`。
3. `draw_state`：`normal`、`draw_pending`、`draw_wait_retry`。
4. `current_issue`：当前可下注期号。
5. `pre_issue` 和 `pre_result`：上一期开奖期号和开奖结果。
6. `close_countdown` 和 `draw_countdown`：本次采集得到的封盘和开奖倒计时。
7. `fetched_at`：共享账号实际采集成功时间。
8. `next_normal_refresh_at`：下一次普通 25 秒采集时间。
9. `next_draw_retry_at`：开奖专项刷新下一次执行时间。
10. `snapshot_version`：快照版本号或递增序号，防止旧采集结果覆盖新采集结果。
11. `message_code` 和 `message_text`：前端简短中文提示和日志编号。

缺少这些字段时，前端、worker 和管理员页面容易各自推断状态，最终出现倒计时、开奖数据、结算状态不一致。

#### 8.2 快照写入必须保证原子性和顺序

共享采集器写入快照时必须保证：

1. 同一 `shared_group_id` 使用单飞锁，避免并发采集互相覆盖。
2. 旧期号、旧开奖结果、旧倒计时不得覆盖更新的 `snapshot_version`。
3. 新期号出现时，必须同时写入采集时间、倒计时、开奖状态和下一次刷新时间。
4. 如果只拿到部分字段，应标记为过程状态，不能把半截数据当成 `shared_ok`。

风险点：如果没有版本保护，开奖专项刷新、普通 25 秒刷新、管理员手动检测可能互相覆盖，造成前端显示新期号但 worker 仍按旧期号结算或下注。

#### 8.3 停盘状态需要恢复规则

`market_closed` 不能只是终态。需要补充恢复规则：

1. 检测到停盘后，停止本期开奖专项刷新。
2. worker 不再为停盘期生成新的下注信号。
3. worker 仍继续处理已有订单结算。
4. 共享采集器应按较低频率继续检测平台是否恢复开盘，避免永远停在停盘状态。
5. 平台恢复后，必须重新拿到有效期号、封盘倒计时、开奖倒计时后，才能从 `market_closed` 回到 `shared_ok`。

风险点：如果没有恢复规则，停盘后即使平台开盘，前端和 worker 也可能一直显示停盘。

#### 8.4 worker 下注前仍需要快照新鲜度保护

虽然 worker 下注前不再请求平台倒计时接口，但不能无条件信任任何旧快照。下注前至少需要检查：

1. 快照没有超过允许新鲜度。
2. 当前期号未过期。
3. 本地计算的封盘截止时间仍在允许下注窗口内。
4. 当前共享状态不是 `market_closed`、`shared_error` 或 `shared_stale`。

如果快照过期或状态异常，应跳过本期下注并给出中文提示，不能拿旧期号继续下注。

#### 8.5 结算必须幂等

结算分支独立后，重试和补偿次数会增加，因此必须保证同一订单不会被重复结算：

1. 以第三方账号、期号、订单号或投注记录 ID 作为幂等键。
2. 已结算记录再次收到平台返回时，只允许补充缺失字段，不能重复累计盈亏。
3. `settlement_pending`、`settled`、`settle_failed` 的状态流转必须单向可追踪。
4. 服务重启后应恢复未完成的待结算记录，而不是丢失或重复计算。

风险点：如果没有幂等保护，结算重试可能造成盈亏重复累加。

#### 8.6 请求频率需要设置硬上限

本方案已经降低 worker 直接访问平台的频率，但仍需要硬上限：

1. 同一共享组同一时间只能有一个采集请求。
2. 同一第三方账号同一时间只能有一个结算请求。
3. 同一第三方账号的下注请求按策略错峰执行，无法错峰时阻止启动并提示策略过多。
4. 多个账号同时结算时允许 0 至 3 秒错峰，但不能改变最长等待 10 分钟的规则。
5. 共享异常时，worker 本地回退必须全局节流到最多 80 秒一次，不能每个策略各自 80 秒。

风险点：如果节流按策略做，而不是按第三方账号或 worker 做，多策略会把请求量重新放大。

#### 8.7 告警需要去重和中文编号

告警展示需要避免刷屏：

1. `draw_pending` 和 `draw_wait_retry` 是过程状态，不生成失败告警。
2. `market_closed`、`shared_error`、`shared_stale` 只在状态变化时告警一次。
3. 结算 10 分钟内未最终失败时，前端显示“结算中”或“待结算”，不提前显示 `settle_failed`。
4. 操作者端只显示简短中文，后端日志保存平台原始返回、请求阶段和日志编号。

#### 8.8 需要补充的验收场景

除前文验收标准外，第一阶段完成后还需要验证：

1. 正常开奖：共享 25 秒普通采集和开奖专项刷新不会并发。
2. 开奖延迟：前端能看到 `开奖数据暂未获取，10秒后再次刷新`，worker 不回退操作者账号高频采集。
3. 停盘：前端显示 `当前处于停盘`，worker 停止新下注但继续结算已有订单。
4. 共享异常：前端显示 `SHARED-002`，worker 80 秒低频自取，恢复共享后回到共享快照。
5. 结算延迟：10 分钟内保持待结算并持续重试，不阻塞下一期下注。
6. 重启恢复：服务重启后能恢复共享采集、worker 运行和待结算记录，不因绑定账号验证状态过期而阻止策略继续运行。
7. 多策略同账号：下注错峰生效，结算按账号聚合，不按策略并发。
8. 多账号同操作者：各第三方账号 worker 独立，第二个账号启动不会顶掉第一个账号。
