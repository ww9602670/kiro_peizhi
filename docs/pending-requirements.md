## 需求一：策略历史数据回测

### 背景
操作者希望在实际投入资金之前，能够使用策略对历史开奖数据进行回测，评估策略的盈亏表现。

### 当前系统现状分析
- 数据库有 `lottery_results` 表（字段：issue, open_result, sum_value, open_time）
- 但数据来源是**被动的**：仅在 `SettlementProcessor` 结算时顺带存储当期开奖结果
- **没有独立的历史数据采集机制**，不会后台持续抓取所有期号的开奖结果
- 如果某一期没有投注，该期的开奖数据就不会被存储
- 因此当前系统**不具备完整连续的历史数据**，无法直接支持回测

### 需要实现的子功能
1. **历史数据采集模块**
   - 后台定时任务，独立于 Worker，持续从平台 API 拉取开奖结果
   - 存储到 `lottery_results` 表，保证数据连续完整
   - 需要考虑：采集频率、停机时段处理、数据去重（INSERT OR IGNORE 已有）

2. **回测引擎**
   - 复用现有策略类（FlatStrategyImpl / MartinStrategyImpl）
   - 用历史数据模拟运行，不真实下注
   - 输入：策略参数 + 历史数据范围（起止期号或日期）
   - 输出：逐期盈亏记录、汇总统计

3. **回测结果统计**
   - 总盈亏、胜率、最大连亏次数、最大回撤
   - 盈亏曲线数据（供前端绘图）
   - 马丁策略的 level 分布统计

4. **后端 API**
   - 创建回测任务
   - 查询回测进度/结果
   - 查询可用历史数据范围

5. **前端回测页面**
   - 策略参数配置表单
   - 历史数据范围选择
   - 回测结果展示（表格 + 图表）

### 待确认问题
- [ ] 历史数据需要保留多长时间？（最近 7 天 / 30 天 / 全部？）
- [ ] 回测是否需要考虑赔率变化？（当前赔率是固定的还是每期不同？）
- [ ] 回测是否需要模拟风控规则（止损/止盈）？
- [ ] 是否需要支持多策略组合回测？

## 需求二：系统容量与压力测试

### 背景
SaaS 平台作为托管服务，需要了解系统能承受的并发极限，以便合理规划资源和定价。

### 核心问题

#### 1. 系统容量上限
需要测试以下场景的系统表现：

| 场景 | SaaS 账号数 | 每账号投注账号数 | 每账号策略数 | Worker 总数 | 策略总数 |
|------|------------|----------------|------------|------------|---------|
| 基础（目标） | 500 | 5 | 10 | 2500 | 25000 |
| 扩展 | 1000 | 5 | 10 | 5000 | 50000 |
| 极限 | 2000 | 5 | 10 | 10000 | 100000 |

#### 2. 两种场景的区别分析（基于代码审查）

**架构层面：**
- 每个**投注账号**对应一个 `AccountWorker` 实例（独立 asyncio Task）
- 每个 Worker 内部维护多个 `StrategyRunner`（纯内存计算，无独立协程）
- 所以关键瓶颈是 **Worker 数量**，不是策略数量

**场景 A（1000 账号 × 1 投注账号 × 1 策略）= 1000 个 Worker：**
- 1000 个并发 asyncio Task
- 每个 Worker 每期需要：1 次 GetCurrentInstall + 1 次 place_bet + 1 次结算
- 平台 API 并发请求：约 1000 × 3 = 3000 次/期
- SQLite 写入：约 1000 条 bet_orders/期
- 内存占用：每个 Worker 约含 7 个组件对象（adapter/session/poller/risk/executor/settler/reconciler）

**场景 B（1000 账号 × 10 投注账号 × 100 策略）= 10000 个 Worker：**
- 10000 个并发 asyncio Task
- 平台 API 并发请求：约 10000 × 3 = 30000 次/期（但同一投注账号共享 session）
- SQLite 写入：约 10000 × 100 = 1000000 条 bet_orders/期（**这是最大瓶颈**）
- 内存占用：10 倍于场景 A

**核心区别：**
- Worker 数量差 10 倍（1000 vs 10000）
- 每期 DB 写入量差 100 倍（1000 vs 100000 条投注记录）
- 平台 API 并发差 10 倍
- SQLite 单文件写入是最大瓶颈（WAL 模式下写入仍然串行）

#### 3. 当前架构瓶颈点
- **SQLite 写入瓶颈**：单文件数据库，WAL 模式下读并发但写串行
- **单进程 asyncio**：所有 Worker 在同一个事件循环中，CPU 密集操作会阻塞
- **内存**：每个 Worker 约 7 个组件对象，10000 个 Worker 的内存开销
- **平台 API 限流**：外部平台可能有请求频率限制

### 4. bet_timing 下注阈值分析

**用户确认的语义：bet_timing = "开奖后 X 秒下注"**

即：当新一期开始后，等待 X 秒再执行下注。这是一个"延迟下注"的概念，用于控制在一期中的什么时间点下注。

**当前实现（代码审查结果）：**

`bet_timing` 字段存在于数据库 `strategies` 表中，前端可配置（5~180 秒），通过 API 传递给 Worker。

但实际下注时机的控制逻辑如下：

```python
# worker.py 中的常量
SKIP_THRESHOLD = 18  # 硬编码：close_countdown_sec <= 18s 时跳过

# _should_bet() 方法
def _should_bet(self, install: InstallInfo) -> bool:
    if install.state != 1:
        return False
    remaining = install.close_countdown_sec
    if remaining <= SKIP_THRESHOLD:  # 使用硬编码的 18s
        return False
    return True
```

**结论：`bet_timing` 字段当前未被实际使用。**

- `bet_timing` 被存储在 DB、传递给 Worker 构造函数（`self.bet_timing = max(5, min(bet_timing, 300))`）
- 但 `_should_bet()` 方法使用的是硬编码的 `SKIP_THRESHOLD = 18`
- `self.bet_timing` 在 Worker 的主循环和下注决策中**没有被引用**
- 改为 10 秒**不会生效**，因为代码没有读取这个值

**需要修复：**
- 语义明确为"开奖后 X 秒下注"
- 修改 Worker 主循环：获取到新期号后，计算已过去的时间，如果不足 bet_timing 则 sleep 等待
- `_should_bet()` 中的 `SKIP_THRESHOLD` 保留为安全阈值（封盘前最少预留时间），与 bet_timing 独立
- 前端描述文案需要更新为"开奖后 X 秒下注"

## 需求四：AI 辅助策略生成

### 背景
当前策略（flat/martin）需要用户手动选择玩法方向和金额参数。用户希望 AI 能分析历史数据，**在策略创建阶段一次性生成一套优化的策略参数**（玩法方向、金额、倍投序列等），生成后的策略与普通 flat/martin 策略完全一样，按固定参数自动运行。

**关键理解（已确认）：AI 只在策略创建/编辑阶段参与，负责"生成策略参数"这一步。策略运行后，AI 不再参与每期的实时决策。运行中的策略行为与手动创建的 flat/martin 完全一致。**

### 核心概念：AI 辅助生成 ≠ AI 实时决策

- AI 的作用是"策略参数顾问"：分析历史数据 → 推荐最优参数组合
- 生成的策略本质上仍是 flat 或 martin 类型，只是参数由 AI 优化
- 策略运行时不调用 AI，不产生额外的 AI 调用成本
- 用户可以在 AI 推荐的基础上手动微调参数

**架构上已预留了扩展点，但未被利用：**

1. `BaseStrategy.compute(ctx: StrategyContext) -> list[BetInstruction]`
   - `StrategyContext` 已有 `history: list[LotteryResult]` 字段，设计上就是给策略提供历史数据用的
   - `BetInstruction` 返回的是 `key_code + amount`，**key_code 本身就是动态的**
   - 也就是说，`compute()` 完全可以每期返回不同的 key_code

2. **但当前 history 字段始终为空：**
   ```python
   # worker.py _collect_signals() 中：
   context = StrategyContext(
       current_issue=install.issue,
       history=[],        # ← 硬编码空列表！
       balance=0,         # ← 也没有填充余额
       strategy_state={},
   )
   ```
   策略拿不到历史数据，自然无法做动态分析。

3. **当前策略的 play_code 是创建时固定的：**
   - `_build_strategy_runner()` 中 `key_codes=[play_code]` 写死在构造函数里
   - flat/martin 的 `compute()` 只是遍历 `self._key_codes` 返回固定方向

**结论：架构上可行，但需要做以下改造：**

### 需要实现的子功能（修正后：AI 仅在策略创建阶段参与）

#### 1. 历史数据查询接口（基础设施）
- 新增 API 接口查询近 N 期 `lottery_results`，供 AI 分析使用
- **依赖需求一的历史数据采集模块**：没有连续完整的历史数据，AI 分析就不准确
- 此接口仅在策略创建/编辑时调用，不在 Worker 运行时调用

#### 2. AI 策略参数生成服务（核心）
- 新建 `AiStrategyGenerator` 服务，在策略创建阶段调用
- 输入：历史数据 + 用户偏好（策略类型 flat/martin、允许的玩法范围、风险偏好）
- 输出：推荐的策略参数（play_code、base_amount、martin sequence 等）
- 用户可以接受 AI 推荐，也可以手动微调后保存
- **生成后的策略就是普通的 flat 或 martin 策略，运行时不再调用 AI**

#### 3. AI 分析引擎的两种实现路径

**路径 A：本地规则/统计模型（推荐先实现）**
- 基于历史数据的统计分析（频率、趋势、冷热号等）
- 内置多种分析算法，用户选择分析偏好
- 优点：无外部依赖、延迟低、成本为零
- 缺点：分析能力有限，本质是统计规则

**路径 B：LLM API 调用（仅在创建时调用一次）**
- 策略创建时将近 N 期数据发送给 LLM，让 AI 推荐参数
- 因为只在创建时调用一次，成本和延迟问题大幅降低
- 优点：分析能力强，可理解复杂模式
- 缺点：需要 API Key 和网络连接

**建议：先实现路径 A（本地统计分析），后续可选接入 LLM 增强。**

#### 4. 策略创建流程变化
- 策略创建表单新增"AI 推荐"按钮
- 用户点击后，系统分析历史数据，返回推荐参数
- 推荐参数自动填入表单，用户可修改
- 最终保存的策略类型仍为 flat 或 martin，参数固定

#### 5. 前端改造
- 策略创建表单新增"AI 推荐参数"功能区
- 配置分析窗口（近 50 期 / 100 期 / 200 期）
- 选择风险偏好（保守 / 均衡 / 激进）
- 显示 AI 推荐理由和置信度
- 用户确认后参数填入表单

### 与其他需求的依赖关系
- **强依赖需求一（历史数据采集）**：AI 分析需要连续完整的历史数据
- **关联需求五（策略排行）**：AI 生成的策略表现可纳入排行榜对比

### 积分扣费机制（已确认，修正为创建阶段扣费）

AI 辅助策略生成每次调用需要扣除积分，具体规则：
- **前置条件**：SaaS 账户积分余额 ≥ 5 才允许调用 AI 生成参数
- **扣费**：每次 AI 辅助生成（策略创建/编辑时点击"AI 推荐"）扣除 **5 积分**
- **余额不足时**：禁用"AI 推荐"按钮，提示充值
- **积分来源**：通过 USDT 钱包充值获得（详见需求六）

**对策略创建流程的影响：**
```
AI 辅助策略生成流程：
1. 用户点击"AI 推荐参数"按钮
2. 前端检查积分余额 ≥ 5，不足则提示充值
3. 后端再次校验余额 → 调用 AI 分析引擎
4. AI 返回有效推荐 → 扣除 5 积分 → 返回推荐参数给前端
5. AI 调用失败/超时 → 不扣积分，提示用户重试
6. 用户确认参数后保存策略（保存不再扣费）
```

**注意**：积分扣除在 AI 返回有效结果后才执行，避免调用失败也扣费。策略运行期间不产生任何 AI 相关费用。

## 需求五：策略排行榜

### 背景
用户希望看到各策略的表现排名，便于参考和选择优质策略。排行榜上的策略可以定价出售，其他用户使用积分购买。

### 当前系统现状分析

**已有数据基础：**
- `strategies` 表有 `daily_pnl`（日盈亏）和 `total_pnl`（总盈亏）字段
- `bet_orders` 表有完整的投注和结算记录
- 可以从现有数据计算：胜率、总盈亏、最大回撤、连胜/连亏等指标

### 需要实现的子功能
1. **排行榜数据计算**

   - 支持多种排序维度：盈亏排名、胜率排名、稳定性排名
   - 支持时间范围筛选：今日、本周、本月、全部

2. **排行榜 API**
   - `GET /api/strategy-ranking` 返回排行数据
   - 支持分页和排序参数
   - 考虑数据隔离：operator 只能看到自己的策略排行？还是全平台公开排行？

3. **前端排行榜页面**
   - 排行榜表格（排名、策略名、类型、玩法、盈亏、胜率等）
   - 时间范围切换
   - 排序维度切换
   - 可选：盈亏趋势小图表

4. **策略定价与购买（已确认）**

   策略拥有者可以将策略上架到排行榜并设置价格，其他用户使用积分购买。

   **上架流程：**
   - 策略拥有者在排行榜中选择"上架出售"
   - 设置策略价格（单位：积分）
   - 上架后排行榜显示价格标签

   **购买流程：**
   - 购买者在排行榜看到策略 + 价格
   - 点击"购买"，系统检查积分余额是否充足
   - 扣除购买者积分 → 复制策略参数到购买者账户下
   - 积分分配：**策略拥有者获得 50%，平台抽取 50%**

   **积分分配示例：**
   ```
   策略价格 = 100 积分
   购买者支付 100 积分
   → 策略拥有者 +50 积分
   → 平台收入 +50 积分（进入平台收益池）
   ```

   **数据模型：**
   - `strategies` 表新增字段：`is_listed`（是否上架）、`price`（积分价格）
   - 新增 `strategy_purchases` 表：记录购买历史（buyer_id, seller_id, strategy_id, price, seller_share, platform_share, purchased_at）
   - 平台收益记录：`platform_revenue` 表或在 `credit_transactions` 中用特殊类型标记

### 待确认问题

- [ ] 如果是全平台排行，是否需要匿名化（隐藏 operator 信息）？

## 需求六：积分系统 + USDT 充值

### 背景
SaaS 平台需要一套积分经济系统，用于 AI 策略调用计费和策略交易。积分通过 USDT 充值获得，是平台内部的虚拟货币。

### 核心规则（已确认）

| 项目 | 规则 |
|------|------|
| 充值方式 | USDT 钱包转账 |
| 汇率 | 10 USDT = 50 积分（1 USDT = 5 积分） |
| AI 策略调用 | 每次扣 5 积分（≈ 1 USDT） |
| 策略购买 | 按卖家定价扣积分 |
| 策略出售分成 | 卖家 50% + 平台 50% |
| 积分最小单位 | 1 积分（整数） |

### 需要实现的子功能

#### 1. 积分账户模型
- `operators` 表新增 `credit_balance` 字段（积分余额，整数）
- 或新建 `credit_accounts` 表（operator_id, balance, frozen_balance, updated_at）
- 所有积分变动必须记录流水（`credit_transactions` 表）

**积分流水表 `credit_transactions`：**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增 |
| operator_id | INTEGER | 所属 operator |
| type | TEXT | 类型：recharge / ai_call / strategy_purchase / strategy_sale / platform_revenue |
| amount | INTEGER | 变动积分（正=收入，负=支出） |
| balance_after | INTEGER | 变动后余额 |
| ref_id | TEXT | 关联 ID（充值订单号 / 策略 ID / 购买记录 ID） |
| description | TEXT | 描述 |
| created_at | TEXT | 时间 |

#### 2. USDT 充值模块

**充值流程：**
```
用户发起充值
    ↓ 选择充值金额（10/50/100/500 USDT 等档位，或自定义）
前端展示平台 USDT 收款地址 + 充值金额 + 转账备注（含用户标识）
    ↓ 用户在自己的 USDT 钱包中转账
后端确认到账（两种方式）
    ↓ 方式 A：人工审核（管理员确认）
    ↓ 方式 B：链上监听（自动确认）
到账后按汇率增加积分 + 记录流水
```

**充值方式分析：**

| 方式 | 实现难度 | 可靠性 | 适合阶段 |
|------|---------|--------|---------|
| A. 人工审核 | 低 | 高（人工确认） | MVP / 初期 |
| B. 链上监听（TRC20/ERC20） | 高 | 高（自动化） | 成熟期 |

**推荐先实现方式 A（人工审核）：**
- 用户提交充值申请（金额 + USDT 交易哈希 TxHash）
- 管理员后台审核：核对 TxHash、金额、到账状态
- 审核通过 → 增加积分 + 记录流水
- 审核拒绝 → 标记原因，通知用户

**充值订单表 `recharge_orders`：**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增 |
| operator_id | INTEGER | 充值用户 |
| usdt_amount | REAL | USDT 金额 |
| credit_amount | INTEGER | 应得积分 |
| tx_hash | TEXT | USDT 交易哈希 |
| wallet_address | TEXT | 用户钱包地址（可选） |
| status | TEXT | pending / approved / rejected |
| reject_reason | TEXT | 拒绝原因 |
| reviewed_by | INTEGER | 审核管理员 ID |
| reviewed_at | TEXT | 审核时间 |
| created_at | TEXT | 申请时间 |

#### 3. 积分消费 — AI 辅助策略生成

与需求四联动：
- 用户点击"AI 推荐参数"时检查 `credit_balance >= 5`
- AI 返回有效推荐后扣除 5 积分
- 记录流水：type=`ai_call`，amount=-5，ref_id=策略 ID
- 注意：仅在策略创建/编辑时产生，策略运行期间不产生 AI 费用

#### 4. 积分消费 — 策略购买

与需求五联动：
- 购买者积分 ≥ 策略价格时允许购买
- 扣除购买者积分（type=`strategy_purchase`，amount=-价格）
- 增加卖家积分（type=`strategy_sale`，amount=+价格×50%）
- 记录平台收入（type=`platform_revenue`，amount=+价格×50%）
- 三条流水在同一事务中完成，保证原子性

#### 5. 后端 API

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/credits/balance` | GET | 查询积分余额 |
| `/api/credits/transactions` | GET | 查询积分流水（分页） |
| `/api/credits/recharge` | POST | 提交充值申请 |
| `/api/admin/recharge-orders` | GET | 管理员查看充值申请列表 |
| `/api/admin/recharge-orders/{id}/approve` | POST | 审核通过 |
| `/api/admin/recharge-orders/{id}/reject` | POST | 审核拒绝 |

#### 6. 前端页面

**Operator 端：**
- 积分余额展示（Dashboard 顶部 / 导航栏）
- 充值页面：选择金额 → 显示收款地址 → 提交 TxHash
- 积分流水页面：收支明细、筛选

**Admin 端：**
- 充值审核列表：待审核 / 已通过 / 已拒绝
- 审核操作：查看 TxHash → 通过/拒绝
- 平台收益统计：策略交易抽成汇总

### 安全考虑
- 积分变动必须在数据库事务中完成（余额检查 + 扣除 + 流水记录原子操作）
- 防止并发扣费导致余额为负（使用 `UPDATE ... WHERE balance >= amount` 乐观锁）
- 充值审核需要二次确认，防止误操作
- TxHash 去重：同一 TxHash 不能重复充值
- 积分不可提现（单向流入），降低合规风险

### 与其他需求的依赖关系
- **需求四（AI 策略）依赖本需求**：AI 调用需要积分余额检查和扣费
- **需求五（策略排行榜）依赖本需求**：策略购买需要积分支付和分成
