# 轻量对冲 UI 需求文档

日期：2026-06-24

## 背景

当前旧桌面 UI 已经包含平台配置、浏览器启动、登录、接管大厅、进房、真实下注执行、状态展示和大量诊断能力。但旧 UI 也混入了较多历史兼容逻辑、高频状态刷新、详细日志刷屏和资源监控显示路径。用户目标不是继续扩展旧 UI，而是基于已经验证过的轻量独立脚本，构建一套更干净、更低资源消耗、可支持 4 账号对冲的新版 UI。

新版 UI 的视觉草图以 `docs/ui-drafts/lightweight-hedge-console-v3.html` 为参考。

## 总原则

1. 不把旧 UI 的高资源消耗逻辑搬到新 UI。
2. 新 UI 先做独立壳，再逐项接入旧 UI 中已经稳定的能力。
3. 旧 UI 的核心状态采集、倒计时、局号、余额、房间、限红、坐标和真实下注链路属于保护区，不能为了新 UI 直接重构或降级。
4. 新 UI 只展示人类需要判断的信息；调试信息默认折叠到高级设置或写入文件。
5. 所有接管、进房、真实下注能力必须通过受控服务接口调用，不允许 UI 线程直接执行浏览器点击或状态探针。

## 范围

### 包含

1. 新增轻量 UI 界面。
2. 平台配置读取、编辑、保存。
3. 平台摘要展示：平台自定义名称、代理到期时间、平台账号。
4. 批量启动、批量填写登录、批量接管、批量进房、批量释放、批量停止。
5. 主号可切换，其余账号自动作为副号。
6. 4 账号状态摘要展示。
7. 高级设置折叠区：调试发一轮、测试 10 轮、观察窗、点击间隔、金额范围、倒计时门槛、确认等待、资源策略。
8. 接入轻量核心脚本的能力：统一发号者、4 账号同步确认、并行执行、执行结果聚合。
9. 执行记录和轻量日志摘要。

### 不包含

1. 不重写当前后端状态机。
2. 不改变当前真实下注点击函数的核心行为。
3. 不改变当前坐标识别、房间识别、局号识别、倒计时识别的生产链路。
4. 不新增高频 canvas 探针或高频前端对象扫描。
5. 不把旧 UI 的完整诊断面板、逐筹码日志、原始 WebSocket 细节、shadow 状态刷屏搬入新 UI。
6. 不让普通用户界面显示调试按钮。

## 用户角色

1. 普通操作者：启动系统、确认 4 平台状态、切换主号、开始/暂停/急停对冲。
2. 高级调试者：展开高级设置，执行测试发一轮、测试 10 轮、观察窗、调点击间隔。
3. 开发/排障者：查看结构化日志文件和诊断文件，不依赖主 UI 刷屏。

## 功能需求

### R1. 新 UI 壳

新版 UI 必须作为独立入口或独立窗口实现，不能直接大改旧 `MainDashboard`。

验收标准：
- 可以单独启动新 UI。
- 有平台配置、运行控制、执行记录三个页面。
- 页面结构与 V3 草图一致或更清晰。
- 未接入后端时也能启动，不崩溃。

### R2. 平台配置页

平台配置页必须只在摘要区展示关键运行资料。

验收标准：
- 每个平台摘要只显示：平台自定义名称、代理到期时间、平台账号、可用/待续费状态。
- 4 平台编辑集中在一个卡片或表格中。
- 支持保存 4 平台配置。
- 支持代理一键自动填写入口。
- 批量启动、批量填登录、批量接管、批量进房、批量释放、批量停止位于摘要下方。

### R3. 主号切换

新版 UI 必须支持 a1/a2/a3/a4 任意账号切换为当前主号。

验收标准：
- 选择一个主号后，其余账号自动显示为副号。
- 接管对象自动变为非主号账号。
- 本轮计划显示跟随主号变化。
- 切换主号只改变计划归属和 UI 显示，不直接触发下注。

### R4. 普通运行区降噪

普通运行区不能显示调试按钮和调参控件。

验收标准：
- 默认只显示主号切换、账号状态、发号门槛、本轮计划、运行摘要、轻量日志。
- 测试发一轮、测试 10 轮、观察窗、点击间隔、金额范围、倒计时门槛、确认等待、资源策略默认折叠在高级设置。
- 普通运行区不出现逐筹码点击日志。

### R5. 平台启动与登录

新版 UI 必须复用旧 UI 已有的平台配置结构和启动/填登录能力，但不得搬入旧 UI 的高频刷新显示逻辑。

验收标准：
- 单平台启动可用。
- 批量启动可用。
- 单平台填登录可用。
- 批量填登录可用。
- 启动和登录状态只以摘要事件刷新 UI。

### R6. 接管与进房

新版 UI 必须复用当前已经验证过的接管大厅和进房能力，且保持无头窗口尺寸、profile、上下文路径一致。

验收标准：
- 主号可保持有头，副号可接管为无头。
- 批量接管只作用于当前副号列表。
- 批量进房支持 4 平台。
- 失败时显示简短原因，并把详细原因写入诊断日志。

保护门禁：
- 此需求接近房间、坐标、状态采集链路，实施前必须单独审核变更范围。

### R7. 轻量核心执行

新版 UI 必须接入独立测试脚本中验证过的轻量核心，而不是旧 UI 的重刷新路径。

验收标准：
- 统一发号者在发送前并行读取 4 账号摘要状态。
- 只有同房、同局、可下注、倒计时满足门槛时才发号。
- 默认门槛为倒计时大于等于 10 秒。
- 4 账号并行执行。
- UI 显示每轮计划、实际、缺口、最长耗时和状态。

保护门禁：
- 此需求接近真实下注链路，实施前必须单独审核变更范围。

### R8. 日志与记录

新版 UI 只展示操作者需要的摘要日志。

验收标准：
- 主 UI 日志只展示：启动、接管、进房、发号、执行完成、缺口、阻断、异常。
- 详细调试日志写文件，不进入主 UI 高频刷新。
- 执行记录按轮次展示：房间、局号、发号倒计时、点击间隔、各账号计划/实际/缺口、最长耗时、状态。

### R9. 资源控制

新版 UI 必须比旧 UI 更轻。

验收标准：
- UI 不主动启动高频状态扫描。
- UI 只订阅轻量摘要事件。
- 状态卡刷新有节流。
- 日志追加有行数上限或批量刷新。
- 高级资源策略显示只展示最近摘要，不做高频写盘。

### R10. 回滚与共存

新版 UI 必须与旧 UI 共存，直到新 UI 人工验证通过。

验收标准：
- 旧 UI 入口不被删除。
- 新 UI 有独立入口。
- 旧 UI 配置文件可被新 UI 读取。
- 新 UI 失败时可以关闭并继续使用旧 UI。

## 非功能需求

1. 新 UI 启动后空闲状态 CPU 占用应明显低于旧 UI。
2. 连续运行时主 UI 不应因日志增长明显卡顿。
3. 关键操作必须有按钮防重复提交。
4. 异常必须 fail closed：状态不同步、房间不同、局号缺失、倒计时不足时不得发号。
5. 配置写入必须使用原子写入或临时文件替换，避免配置文件损坏。

## 验收流程

1. 文档审核通过。
2. 阶段 1-3 实现并测试：UI 壳、配置、启动登录。
3. 人工确认接管/进房变更范围后，阶段 4 实现。
4. 人工确认真实执行接入范围后，阶段 5 实现。
5. 阶段 6 日志、异常、资源摘要完成。
6. 交付人类在真实平台测试。

## 明确禁止

1. 禁止直接复制旧 UI 的全量 `MainDashboard` 到新 UI。
2. 禁止在新 UI 主线程运行浏览器探针。
3. 禁止把 `state_v2_shadow`、canvas 文本、WebSocket 原始包作为 UI 高频刷新源。
4. 禁止 UI 逐筹码刷屏。
5. 禁止 UI 在未通过同房、同局、可下注、倒计时门槛时发号。
6. 禁止为降低资源而关闭会影响 H5 渲染、坐标识别或真实点击的浏览器能力。
