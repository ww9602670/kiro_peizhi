# 第三方账号会话与多策略执行整改需求

日期：2026-05-02

## 当前现状

当前系统存在多条第三方平台登录链路：

1. 绑定账号只写入数据库，不登录第三方平台。
2. 重新验证账号会创建临时平台连接，登录后拉余额、探测盘口、拉赔率，然后关闭连接。
3. worker 启动后会再创建自己的平台连接，并再次登录。
4. 手动刷新赔率会另外创建平台连接并登录。
5. worker 心跳、拉期号、结算恢复失败时，也可能触发重登。

因此，前端看到的“账号已验证”和 worker 实际使用的下注会话不是同一条链路。验证成功后保存到数据库的状态不能代表 worker 会话仍然在线。

当前余额显示也不是实时平台余额。前端仪表盘读取的是本地数据库余额，数据库余额主要由验证、真实下注本地扣减、结算后平台余额同步等动作更新。平台余额接口异常时，不应把异常结果误判为真实余额 0。

当前多策略执行已有基础能力：

1. 同一个 `account_id + platform_type` 会进入同一个 worker。
2. 已有 worker 时，新启动策略会热更新进现有 worker。
3. 策略有 `bet_timing`，默认 88 秒，允许范围 10-100 秒。
4. 当前已有同账号同方向策略 20 秒间隔校验与自动调整逻辑。
5. worker 会按 `bet_timing` 分组执行同一期策略。

但现有能力还没有和统一会话、多账号并行、平台限流完整合并。

## 目标需求

本次整改目标是把第三方账号运行链路收口为可控、可解释、可测试的统一机制：

1. 同一个第三方物理账号只能有一条运行态登录会话。
2. 验证账号、刷新赔率、worker 下注、worker 结算、余额同步、心跳恢复必须走统一会话入口。
3. 同一账号同一时间只允许一个登录或重登动作。
4. worker 正在运行时，手动验证和刷新赔率不得另起登录顶掉 worker。
5. 同一个账号的真实下注、结算、余额同步等平台请求必须串行。
6. 多策略可以并行计算信号，但提交平台必须按账号队列执行。
7. 多账号可以并行运行，但同平台共享组需要限流，避免集中登录、集中验证码、集中下注、集中结算。
8. 新建、编辑、启动策略时必须自动检测下注时机，真实下注策略默认按 20 秒间隔分隔。
9. 下注时机默认 88 秒，允许范围 10-100 秒。
10. 同账号、同盘口、同方向策略应优先使用 88、68、48、28 等间隔点，无法分配时阻止创建或启动并给出明确原因。
11. 平台余额接口异常时，保留上一次可信余额，标记同步失败，不得误判为 0。
12. 遇到 403、Cloudflare、验证码异常、平台风控信号时，必须停止自动高频重试并告警。
13. 共享开奖账号只提供开奖、期号、倒计时数据，不得和真实下注账号共用会话。

## 场景要求

### 单账号多策略

同一个操作者、同一个第三方账号、同一个盘口运行多个策略时：

1. 只能启动一个 worker。
2. 只能使用一条平台登录会话。
3. 多个策略进入同一期执行计划。
4. 按下注时机分组。
5. 同一组策略可以合并或顺序生成订单。
6. 最终真实平台提交必须串行。

### 多账号并行

同一个操作者绑定多个第三方账号并运行策略时：

1. 每个物理账号独立会话。
2. 每个物理账号独立 worker 或运行上下文。
3. 多账号可以并行计算和运行。
4. 同平台共享组下的登录、验证码、余额、赔率、结算、下注必须受平台级限流约束。

### 同账号不同盘口

同一个第三方账号同时使用多个盘口时：

1. 登录会话所有权必须按物理账号收口。
2. `platform_type` 只是同一会话下的逻辑盘口。
3. 如果无法证明同一会话可安全操作多个盘口，则不得允许同一物理账号同时运行多个真实盘口 worker。

### 重复绑定

同一个第三方平台账号通过不同网址重复绑定时：

1. 应识别为同一个物理账号。
2. 不允许同时真实下注。
3. 不允许因重复绑定产生多条登录会话互相顶号。

## 非目标

本次整改不包含：

1. 修改任何策略算法的选号、马丁、平注、结算规则。
2. 修改共享开奖采集频率。
3. 修改管理员授权策略逻辑。
4. 修改前端页面结构。
5. 新增外部依赖。
6. 做破坏性数据库迁移。
7. 删除历史订单、投注记录、结算记录。

如实现过程中发现必须超出上述范围，必须停止执行并上报原因，不得自行扩展。
