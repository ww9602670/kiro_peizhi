# 轻量对冲 UI 改动与局号停更调查文档

更新时间：2026-06-26

## 1. 保护说明

当前项目的局号、余额、状态机、倒计时、房间、限红、坐标定位链路属于最高优先级保护区。

本文件只整理需求、风险、调查结论和后续任务。没有直接修改运行链路代码。后续如果要改局号采集、状态判断、自动进房、坐标、下注前检测，需要先确认风险，再按最小改动执行。

## 2. 本轮需要整理的改动

### 2.1 三号降级后恢复四号

目标：当某个账号因为余额不足或异常被剔除后，剩余 3 个账号可以继续下注；后续被剔除账号恢复后，可以用一个明确开关补回 4 号运行。

建议方案：

- 不放到高级设置里，入口直接放在“本轮计划”账号卡片上。
- 正常参与账号显示“下局剔除”按钮。
- 已点击剔除后显示“待剔除”，并提供“取消剔除”。
- 已剔除账号显示“下局恢复”按钮。
- 已点击恢复后显示“待恢复”，并提供“取消恢复”。
- 剔除和恢复默认都在下一局生效，不能在本局已经生成计划或正在点击时强行插入。
- 被补回账号必须满足：已登录、在同房、局号同步、余额达到阈值、可下注状态正常。
- 原主号被剔除后，恢复主号策略使用“余额最多优先”或用户指定继承账号。
- 被剔除账号不能继续阻塞 3 号模式的同房、同局、可下注判断。
- 如果剔除后只剩 2 个账号，自动停止下注并提示“少于 3 个账号，无法对冲”。

本轮计划卡片建议显示：

```text
a1 · 主号方向 · 正常       [下局剔除]
a2 · 副号对冲 · 正常       [下局剔除]
a3 · 已剔除 · 余额不足     [下局恢复]
a4 · 待剔除 · 下局生效     [取消剔除]
```

### 2.2 运行摘要不应 100 轮封顶

需要确认 UI 现在是否只是显示最近 100 条执行轮次，还是后端累计轮次被限制。

目标：

- 运行摘要的“测试轮次/执行轮次”累计值不封顶。
- 执行轮次表可以只保留最近 N 条，避免 UI 卡顿。
- 累计值和最近表格分开计算，不能因为表格裁剪导致总数停在 100。

### 2.3 运行计时器

最新打包版需要恢复运行计时器。

目标：

- 启动轻量控制后显示运行时长。
- 暂停时计时保持。
- 停止或重启执行时按设计决定是否清零，建议停止后清零，暂停不清零。

### 2.4 掉线或不在房间后的自动进房

现有链路重点：

- UI 状态轮询约 2 秒一次。
- 无头账号进房重试有节流，避免频繁点击。
- 当前自动进房更偏向“看到大厅状态后再重新进房”。

需要完善：

- 区分“大厅”“在房但局号停更”“在房但不可下注”“浏览器失联”。
- 只有进入过目标房间的账号，才启用自动回房。
- 如果账号在房间里但局号长时间不更新，不应继续当作正常账号。
- 自动进房应有进度展示：等待、点击中、加载中、进房完成、失败原因。
- 批量进房应并行执行，不能一个账号慢导致其他账号长时间等待后被踢。

### 2.5 页面布局压缩

目标：减少滚动，让主要运行信息一屏看清。

建议排版：

- 主区域：账号状态、单账号盈亏。
- 右侧：本轮计划、运行摘要。
- 高级设置区：下注流水累计、最近执行轮次明细、余额阈值。
- 下注流水和执行轮次可以压缩高度，默认折叠或移到高级设置。
- 单账号盈亏移到更醒目的区域，显示初始余额、当前余额、充值/提现修正、当前盈亏。

### 2.6 副号金额分配更不规律

当前副号下注金额看起来过于平均或规律。

目标：

- 副号分配金额在满足筹码规则、步数不超过 5 步、总对冲金额正确的前提下，更接近自然随机。
- 支持 4 元筹码。
- 避免固定拆分，如长期出现 50/50/40 或 100+20+20 这种明显模式。
- 每个计划必须先通过筹码可拆分校验，再进入执行。

### 2.7 可下注显示颜色

目标：

- 可下注：大字使用绿色。
- 不可下注：恢复蓝色。
- 数据过期或局号停更：使用明确的异常样式，不要和不可下注混淆。

### 2.8 计划轮次统计

目标：

- 本轮计划区域增加计划轮次。
- 主号颜色和副号区分，主号建议使用土黄色或其他稳重色。
- 庄/闲用中文显示。

### 2.9 充值和提现记录

目标：中途充值或提现后，单账号盈亏仍然正确。

建议公式：

- 盈亏 = 当前余额 - 初始余额 - 充值累计 + 提现累计
- 盈利为正数，使用蓝色。
- 亏损为负数，使用红色。
- 初始余额以 UI 启动时第一次读到的余额为准，不因暂停、重新启动执行而改变。

说明：之前描述里写到“充值 100，则初始金额 -100 - 当前金额”。从盈亏含义看，更合理的是当前余额减去初始余额，再扣除充值，加入提现。这样充值不会被误算成盈利，提现不会被误算成亏损。

## 3. 局号停更问题调查

### 3.0 当前代码链路定位

新轻量 UI 当前使用的是轻量探针适配器，不是旧 UI worker 事件流。

关键入口：

- `bet_desktop/ui/run_lightweight_dashboard.py`
- `bet_desktop/ui/lightweight_probe_adapter.py`
- `scripts/live_interval_acceptance_probe.py`
- `bet_desktop/backend/cluster_process_worker.py`
- `bet_desktop/browser/live_runtime_state.py`

局号不是从单一位置读取，而是由几路信息合并：

- canvas 识别到的局号。
- 页面运行对象里的局号。
- 下注保护快照里的局号。
- 前端对象扫描里的局号。

轻量探针里当前优先级是：canvas 局号优先，其次页面对象、保护快照、前端扫描。

这意味着：只要最高优先级的数据源停在旧局，UI 和发号阀门就可能持续拿到旧局号。

### 3.1 现象

出现过以下情况：

- 账号明明还在房间里，UI 仍显示大厅或数据过期。
- 有头页面已经换局，但 UI 局号没有跟着变。
- 某些无头账号显示 `BjlGameRoomHallSceneView` 或 `BjlGameSceneView`，但局号不更新。
- 剩余 3 个账号本应继续执行，但仍被缺失账号阻塞。

### 3.2 当前状态来源

新轻量 UI 当前运行入口使用的是轻量探针适配器：

- `bet_desktop/ui/run_lightweight_dashboard.py`
- `bet_desktop/ui/lightweight_probe_adapter.py`
- `scripts/live_interval_acceptance_probe.py`

状态来源主要包括：

- 页面运行对象：房间、局号、状态、倒计时、余额。
- 前端对象扫描：补充房间、局号、状态信息。
- canvas/文字识别：补充局号、倒计时、画面状态。
- 加载状态检测：判断当前是大厅、房间，还是加载中。

### 3.3 关键证据

近期状态文件里出现过这种组合：

```text
a2 game=True room=T001 round=50-1782411094-8543227564
a3 game=True room=T001 round=50-1782431756-8543852365
a4 game=True room=T001 round=50-1782431756-8543852365
a1 game=True room=T001 round=-
```

这说明问题不是单纯 UI 没刷新，而是后端给 UI 的状态里已经出现了“在同房，但某账号局号停在旧值或缺失”。

日志还显示部分账号反复出现：

```text
retry_enter_room_hall_ready_restored
retry_enter_room_result ok=true
```

这说明系统曾判断账号回到大厅并尝试重新进房，但后续仍可能出现局号停更。

### 3.4 根因判断

当前最可能的根因是：状态源发生了“在房但局号源停更或错源”。

具体来说：

1. 有些账号虽然画面还在房间，但页面内部对象可能停在旧局号。
2. 有些账号的加载状态会短暂或持续显示大厅场景，但坐标、房间号、余额还像是在房间。
3. 系统当前把“有房间证据或坐标证据”当作仍在房间，但这不代表局号一定还在更新。
4. 自动进房重试主要依赖“大厅且不在房间”的判断；如果账号被判断为仍在房间，就不会触发重进房。
5. 当前缺少“局号长时间不变”的独立保护阀门。

所以会出现：账号看起来在房间，余额也能读到，但局号已经不再跟随真实牌局变化。

### 3.5 为什么下一局有时又恢复

补充判断：现在最危险的组合是“有房间号、余额或坐标证据，所以系统认为账号还在房间；但局号来源已经缺失或停在旧值”。自动进房更容易在“明确大厅且不在房间”时触发，因此这种“在房但局号停更”的账号不会被及时修复，也可能继续阻塞发号。

因为多个状态源同时存在：

- 页面对象可能某一轮读不到。
- canvas 或文字识别可能下一轮重新识别到。
- 加载状态可能从大厅场景恢复成游戏场景。
- 重新进房后，页面对象重新初始化。

因此局号停更不是每次永久失败，可能下一局或重新加载后恢复。

### 3.6 为什么不能只看“是否在房间”

是否在房间只能说明页面还在牌桌环境，不代表下注所需信息都正常。

下注至少还需要：

- 同房。
- 同局。
- 可下注区间。
- 余额满足。
- 坐标和筹码可点击。

如果局号不更新，系统就无法确认 3 个或 4 个账号是否同一局下注，继续执行会增加错局下注风险。

## 4. 建议修复方向

### 4.1 增加局号新鲜度保护

新增“局号停更”判断：

- 账号显示在房间内。
- 有余额或坐标证据。
- 但是局号缺失超过 N 秒，或局号长时间不变化。
- 其他账号已经进入新局，而该账号仍停在旧局。

满足以上条件时，状态显示为“局号停更”，不能继续当作正常账号。

### 4.2 局号停更后的轻量处理

默认只做轻量处理：

1. 标记“局号停更/数据过期”。
2. 该账号不继续当作正常账号参与同局和发号判断。
3. 不为此新增主动高频刷新、频繁重进房或浏览器重启。
4. 若现有低频自动回房机制已经触发，只记录进度和结果。
5. 如需新增恢复动作，必须单独评估风险后再执行。

### 4.3 三号模式下的检测阀门

如果某账号已经被剔除：

- 同房判断只看剩余账号。
- 同局判断只看剩余账号。
- 可下注判断只看剩余账号。
- 计划生成只使用剩余账号。
- 被剔除账号不能阻塞发号。

### 4.4 账号剔除与补回阀门

账号剔除和补回都从“本轮计划”卡片操作，不放到高级设置。

- 正常账号可以点“下局剔除”。
- 待剔除账号可以点“取消剔除”。
- 已剔除账号可以点“下局恢复”。
- 待恢复账号可以点“取消恢复”。
- 默认不在当前局中途改变参与账号。
- 等下一局计划生成前检查剔除和恢复。
- 满足同房、同局、余额、可下注后再补回。
- UI 显示“待剔除”“已剔除”“待恢复”“恢复失败原因”。
- 剔除后如果只剩 2 个账号，停止发号并提示原因。

## 5. 需要验证的测试

### 5.1 离线逻辑测试

- 4 号正常生成计划。
- 1 个账号余额不足后，自动切换 3 号计划。
- 被剔除账号不再阻塞同房同局判断。
- 余额恢复后，下一局按开关补回 4 号。
- 局号缺失超过阈值后显示“局号停更”。
- 局号停更账号不参与发号。

### 5.2 实盘观察测试

建议观察至少 50 局：

- 每局局号是否及时变化。
- 可下注/不可下注是否稳定切换。
- 掉房后现有低频自动回房是否按冷却机制工作。
- 3 号降级后是否继续执行。
- 4 号补回是否只在下一局生效。
- 执行轮次是否超过 100 后继续累计。
- 运行计时器是否持续显示。

## 6. 风险

这些修复会接触局号、状态、进房、发号阀门，属于高风险保护链路。

主要风险：

- 误判局号停更，导致可下注时被跳过。
- 如果新增自动重进房过于积极，可能打断本来正常的页面。
- 3 号模式阀门放宽过度，导致不同步下注。
- 4 号补回时机不当，导致中途插入计划。

因此建议后续实现时只做最小改动，并保留旧状态字段，新增判断字段，不直接删除已有采集链路。

## 7. 最新 exe 与 V5 排版差异

### 7.1 当前最新打包版本

当前已确认的最新打包版本：

- `release-candidates/LightweightHedgeConsole_20260626_three_account_gate_fix/LightweightHedgeConsole/LightweightHedgeConsole.exe`
- `dist/LightweightHedgeConsole/LightweightHedgeConsole.exe`

打包入口：

- `LightweightHedgeConsole.spec`
- `bet_desktop/ui/run_lightweight_dashboard.py`

当前运行入口使用：

- `LightweightProbeAdapter` 轻量核心。

结论：当前最新 exe 使用的是轻量探针链路，不是旧 UI worker 链路。

### 7.2 当前 exe 真实运行页结构

当前 exe 的运行页结构：

- 左侧：运行控制 + 高级设置。
- 中间：账号状态 + 下注流水累计 + 执行轮次。
- 右侧：本轮计划 + 运行摘要 + 单账号盈亏。

V5 设计目标：

- 左侧：运行控制 + 高级设置 + 下注流水累计。
- 中间：账号状态 + 单账号盈亏。
- 右侧：本轮计划 + 运行摘要。
- 不再放轻量日志。

说明：V5 当前仍是静态设计稿，最新 exe 尚未采用 V5 排版。

### 7.3 需要补充

1. 本轮计划卡片按钮。

当前真实代码还没有：

- 下局剔除。
- 取消剔除。
- 下局恢复。
- 取消恢复。

风险：中等。只做 UI 按钮是低风险，但按钮真正影响下局计划后，会进入发号名单和计划生成逻辑，风险升高。

2. 手动剔除/恢复状态。

需要新增：

- 待剔除。
- 已剔除。
- 待恢复。
- 恢复失败原因。

风险：中高。因为它会影响哪些账号参与计划、哪些账号参与同房同局判断。

3. 运行轮次累计不封顶。

当前控制器仍保留最近 100 条执行结果。正确做法是：

- 累计统计不封顶。
- 执行轮次表只显示最近 N 条。

风险：低到中。需要避免 UI 表格无限增长导致卡顿。

### 7.4 需要修改

1. 按 V5 调整真实 PyQt 排版。

修改内容：

- 把“下注流水累计”从中间移到左侧高级设置下方。
- 把“单账号盈亏”从右侧移到中间。
- 右侧只保留“本轮计划”和“运行摘要”。

风险：低。主要是 UI 布局移动，不碰下注、坐标、局号采集。

2. 单账号盈亏视觉压缩。

当前真实代码已经有每账号充值/提现输入，但排版比 V5 更占空间。需要改成每张账号卡更清晰的独立入口。

风险：低。只影响展示和人工录入。

3. 进房按钮样式统一。

最新真实代码已经有 1/2/3 房选择、副号进房、全部进房。这里不是功能缺失，只需要和 V5 样式统一。

风险：低。

4. 执行轮次表移动到高级明细/折叠区。

当前执行轮次在中间主区域，占空间。V5 里应移到高级明细。

风险：低。只影响显示位置。

### 7.5 需要大改

1. “下局剔除/下局恢复”真正接入计划生成。

这不是单纯加按钮。需要让下一局计划生成前读取人工操作状态，决定参与账号。

风险：中高。若处理不好，可能出现账号被错误排除、恢复时机不对、3 号/4 号切换阻塞。

2. 被剔除账号不参与同房同局阀门。

当前 3 号降级已有部分逻辑，但手动剔除/恢复后也必须严格遵守：被剔除账号不能继续阻塞剩余账号发号。

风险：中高。会影响发号阀门。

3. 局号停更处理链路。

“在房但局号不更新”需要新增局号新鲜度标记和发号隔离，不默认新增恢复动作。

风险：高。这个会触碰局号、状态机和发号阀门，必须小步修改、单独验证。

### 7.6 不建议重构

目前不建议重写轻量核心或重构整个 UI。应该做局部改造：

- UI 排版局部调整。
- 统计累计和最近表格拆开。
- 计划参与名单增加人工剔除/恢复状态。
- 局号停更单独加保护阀门，不默认加主动恢复。

真正需要结构性整理的只有一处：把运行统计拆成两套数据，累计统计和最近执行表分开。这个属于小型重构，风险中等，但必要。

### 7.7 总体风险判断

- 纯 V5 排版落地：低风险。
- 轮次累计不封顶：低到中风险。
- 本轮计划增加剔除/恢复按钮但不接逻辑：低风险。
- 剔除/恢复接入真实计划和发号阀门：中高风险。
- 局号停更检测和发号隔离：高风险，需要单独做，不能和 UI 排版混在一起改。
- 新增主动恢复、重进房或重启浏览器：暂不作为默认目标，若要做必须另开高风险任务。

建议实施顺序：

1. 先做低风险 UI 排版和统计修正。
2. 再做剔除/恢复按钮和状态。
3. 再接入剔除/恢复到计划生成和发号阀门。
4. 最后单独处理局号停更标记和发号隔离。
